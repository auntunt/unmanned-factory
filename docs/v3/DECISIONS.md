# v3 关键设计决策

## 1. 工厂拥有任务生命周期，模型拥有局部执行

需求、验收、预算、版本、任务状态和外部交付属于工厂。模型进程可以替换、中断或失败。它返回的自然语言不能直接把任务标成成功；项目配置的检查与实际 Git 产物共同构成交付证据。

采用现有 ProviderRequest / ProviderResult 边界复用 Codex、Claude、DSH。新增运行时需要实现同一输入输出、超时、取消、事件和费用契约。Pi 尚未接入；Hermes 当前属于本机诊断与既有运维流程，不冒充第四种已验证 SDK。

## 2. 轻量部署，明确扩展条件

第一版是模块化单体：FastAPI + SQLite WAL + 一个持久队列协调器 + 有界工作池，前端静态文件同源服务。独立 Git 工作区承载代码任务。OS 文件锁阻止两个进程同时调度同一个数据库。

这种部署适合当前单所有者和可信环境。它不支持多租户隔离或多机器分布式派发。出现跨主机执行需求时，将 DurableQueue 替换为有租约和心跳的队列，并把工作区位置变成 Worker 所有的资源；保持 Run、Task、Attempt、Event、Capability 的标识和语义。

## 3. 确定性控制与动态分工并存

规划 Agent 从需求和仓库上下文生成有向无环任务图。任务包含修改范围、依赖、复杂度、风险与可信检查名称。程序依据范围冲突和依赖安排可并行工作，再合并到集成工作区执行最终检查。

模型分档是可解释规则：小范围低风险优先经济模型，中等任务常规模型，高复杂度或高风险强模型。失败后可在 1～3 次总尝试内升级。升级修复拥有相同授权范围，不能为了通过检查自行改写验收。角色映射由运行配置提供，角色名称不等于某个供应商固定型号。

## 4. 自主运行是预先授权的产品模式

项目设定一次自主范围，日常需求达到执行条件就自动开始。规划中的业务问题必须回答后继续；工程细节优先由 Agent 查仓库解决。每个 Run 冻结策略、模型配置、上下文与能力版本，后续编辑不会悄悄改变已派发工作。

旧项目保持 supervised；新建项目可默认显式启用 autonomous。未知费用继续策略与自动发布分别配置。预算是下一次派发的约束，正在执行的模型调用可能超过剩余金额；任务数、时长、并发和尝试上限提供额外边界。

## 5. 恢复不能靠重新播放整段对话

队列意图与运行记录落库后再派发。重启恢复 received 和 queued；只读规划可重做，若已发起但未拿到用量结果，补记费用未知。running、verifying、publishing 保留工作区和检查点并标记异常，避免把尚未核对的外部写入再次执行。

人工点击重试创建关联的新 Run，重复点击只产生一个后继。任务内的自动修复则归属同一个 Run 的不同 Attempt。两者的费用、范围和历史不会混在一起。未来需要自动恢复已发生的云端写入时，适配器必须先实现按业务键查询结果及幂等提交，不能依赖提示词保证“不重复”。

## 6. Agent 是可版本化资产

一个能力包含职责、SOP、输入、输出、验收与来源。项目绑定某个明确版本；调用会冻结快照。修改能力产生新版本，不自动升级已有绑定。导出包含 agent.json、SKILL.md、README 与来源运行证据，可迁移配置。

成功交付自动生成草稿材料。草稿保留原始需求与验证证据，目前提炼是确定性归档，不代表模型已学会跨项目通用经验。ready 表示已配置调用契约；它不等于在所有客户环境已认证。把经验升级为通用能力仍需要明确适用条件和新的验收样例。

## 7. 看板是一组事实视图

当前状态决定待处理列表，历史失败不自动构成待处理事项。费用汇总来自每次实际记录的调用，包含规划、失败和修复；未知金额始终单独呈现。事件时间线用于查看依据摘要、选型、动作与验证，导出包含所有已记录事件。

摘要可以截断以保护页面性能；过长事件另存压缩归档并校验摘要，导出取完整归档。上游 SDK 原本没传出的内容不会被虚构补全。凭据脱敏，内部推理不作为产品日志。

## 8. 运维与行业产品如何继续接入

能力库提供项目维护、云部署、飞书汇报、API 集成和旧系统迁移五种草稿。前三者沉淀工厂的日常工作，后三类客户需求来自通话里的维护、迁移和接口集成场景。

当前能力通过工程任务执行链调用，继承仓库范围与可信检查。生产云资源管理还需要目标环境、凭据、可验证结果和恢复规则。运维适配器应接受目标与配置版本，返回外部资源 ID、操作状态、费用和证据，并提供查询与恢复方法。客户配置放在项目档案，通用 SOP 放在能力版本，凭据由运行环境提供。能力定义中不复制客户秘密，也不将单项目成功直接推广成行业事实。
