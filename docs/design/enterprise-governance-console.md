# webuddy 企业组织权限与领导控制台

> 状态：产品方向已确认，实施细节待分阶段设计
> 日期：2026-09-23

## 1. 一句话定位

**webuddy 是与底层 Agent 无关的企业 AI 工作管控平台：向下组装人员、Agent 与工具完成工作，向上让每一层管理者在授权范围内看结果、控风险、管预算、做审批、追责任。**

当前的员工工作台不删除；它是执行面。新增的领导控制台是管理面。两者共用同一套任务、组织、权限、预算和证据事实，不做两套孤立系统。

## 2. 当前问题

当前产品已有项目、运行、职能体、成果、用量和审计的工程基础，但组织模型仍是扁平的：

- 账号只有全局 `admin` 和 `member` 两档；
- 成员直接绑定项目，没有公司、事业部、部门、小组的上下级关系；
- 管理员基本是“看到全部”，无法只管理自己的组织子树；
- 团队、用量与预算入口被放在“工程总览”下，语言和信息架构仍属于员工；
- 首页回答“我怎么开始做事”，没有回答领导的“组织正在产出什么、哪里失控、需要我决定什么”。

因此，给管理员增加几个管理表格还不够。产品需要从“员工工作台 + 超级管理员”升级为“可按组织范围授权的管理与执行一体化平台”。

## 3. 两个工作面

### 3.1 员工工作台

围绕个人与项目的当前工作：

- 开始任务、追加材料、干预与继续；
- 使用被授权的职能体、Skill、工具和执行器；
- 查看自己参与的项目、执行过程、验证证据与成果；
- 处理分配给自己的补充、验收和审批事项。

### 3.2 领导控制台

围绕组织子树的成果与风险：

- **组织总览**：正在进行、待处理、已交付、阻塞趋势和关键成果；
- **待我决定**：预算超额、高风险动作、发布、权限提升、异常调用和人工验收；
- **项目组合**：目标、进展、交付可靠性、风险、负责人与投入；
- **组织与授权**：组织树、人员、职能 Agent、役位、项目和资源授权；
- **成本与容量**：按组织、项目、能力和执行器聚合的预算、用量和异常；
- **Agent 治理**：允许使用哪些执行器、职能体、Skill 和工具，可执行什么动作；
- **审计与合规**：谁在什么范围做了什么，使用了哪个版本、凭据和批准。

领导默认看汇总、异常和决策项，而不是员工的全部对话和日志。只有在具备明确权限且业务上必要时才下钻到原始证据。

## 4. 递归组织，不是无界管理员

组织单元使用树形结构：

```text
公司
├─ 事业部
│  ├─ 部门
│  │  ├─ 小组
│  │  └─ 项目组
│  └─ 共享能力中心
└─ 直属项目
```

同一个人在不同范围可以有不同角色。例如，某人可以是公司的普通成员、A 部门的负责人、B 项目的审批人。角色不再是用户账号上唯一的全局标签。

“管理者—下属”递归的真正含义是：

1. 管理者在自己的组织子树内获得被授予的能力；
2. 可以把不超过自己的权限继续委派给下属负责人；
3. 上级策略向下继承，下级只能在允许范围内收紧或配置；
4. 跨组织访问需显式授权，不因“也是管理者”自动打通；
5. 每次授权、委派、批准、撤销与策略变更都留不可抹除的审计记录。

## 5. 权限模型

不以“页面能否打开”作为权限核心，而是使用可审计的动作授权：

```text
主体 Principal + 作用域 Scope + 动作 Action + 资源 Resource + 条件 Condition
```

主体可以是人、服务账号或职能 Agent；作用域可以是本人、项目、组织节点或组织子树。

首批稳定动作建议为：

| 域 | 关键动作 |
|---|---|
| 工作 | `work.create` `work.read` `work.intervene` `work.cancel` |
| 交付 | `delivery.review` `delivery.approve` `delivery.publish` |
| 组织 | `org.read` `member.invite` `member.assign` `role.delegate` |
| 成本 | `usage.read` `budget.allocate` `budget.override` |
| Agent | `agent.use` `agent.configure` `skill.publish` `tool.authorize` |
| 治理 | `policy.manage` `audit.read` `runtime.manage` |

策略冲突使用稳定规则：明确拒绝优先；组织上级的硬限制不可被下级放宽；高风险动作即使具备执行权，仍可被条件策略要求二次审批。

## 6. 人和 Agent 统一管控，但不混为一类

人、职能体、执行器和工具都可被组织节点授权，但它们的责任不同：

- **人**：承担业务责任，可委派、审批和验收；
- **职能 Agent**：承载岗位方法、上下文与工具边界，不自动拥有业务授权；
- **执行器**：Codex、Claude Code 或其他 runtime，只在一次执行租约中获得最小权限；
- **Skill 与工具**：是可热插拔能力，必须有来源、版本、适用范围和验证状态。

任务在执行前生成“有效权限快照”，记录当时的人、组织、项目、Agent、执行器、Skill、工具和策略版本。中途换执行器不改变任务责任与审计链。

## 7. 领导首页必须回答的五个问题

1. 我负责的范围当前有哪些关键成果？
2. 哪些项目、任务或能力处于风险中？
3. 哪些事项必须由我决定？
4. 我们投入了多少预算与算力，得到了什么交付？
5. 某个结果由谁负责、使用了什么能力、经过什么验证与批准？

首页指标不以“Agent 数量”、“对话数量”或“生成代码行数”冒充管理价值。优先呈现交付结果、周期、阻塞、返工、验收、风险和成本。

## 8. 导航与身份体验

登录后按有效职责进入默认工作面：

- 普通成员：进入“我的工作”；
- 项目负责人：进入“项目控制台”；
- 部门负责人：进入“团队控制台”；
- 企业管理者：进入“组织控制台”。

同时拥有执行与管理责任的人，可在顶部切换“工作 / 管理”，并明确显示当前组织范围。不把所有领导功能继续塞进“工程总览”的子页签。

## 9. 与 AWS Bedrock 参考思路的关系

AWS Bedrock 的 multi-agent collaboration 使用 supervisor 与 collaborator 组织专业 Agent，并区分“汇总协调”与“直接路由”模式。它证明了层级化协作的产品可理解性，但 webuddy 的重点不是复制其 Agent 编排，而是把类似层级用于企业用户、组织范围和委派权限。

要借鉴的是：

- 上级能看懂下级的职责与能力；
- 请求在清晰的责任边界中路由；
- 上下文是否下传受控；
- 所有协作有统一入口和可观测记录。

不要照搬的是：把组织权限等同于 Agent 提示词层级，或把管理判断交给模型自由推理。权限、预算、审批、风险等级和审计必须是确定性的系统事实。

## 10. 与底层 Agent 无关的热插拔边界

webuddy 的长期壁垒是稳定的管控契约，而不是某个 Agent 的调用方法。可热插拔的部分包括：

- 执行器适配器；
- 模型提供方；
- 职能体与 Skill 包；
- 工具、数据源与知识源；
- 验证器、风险规则与审批流；
- 事件、审计和通知出口。

不随插件变动的是：组织范围、有效授权、任务身份、预算租约、幂等与取消、成果归属、证据链和审计记录。

## 11. 分阶段实施

### P0：产品表达与信息架构

- 确定“员工工作台 + 领导控制台”双工作面；
- 出领导首页、组织树、待决定和项目组合的可演示原型；
- 完成领导演示口径，只使用有真实数据来源的指标。

### P1：组织与授权基座

- 新增组织节点、成员关系、范围角色、权限策略与委派记录；
- 将散落的 `role != member` 判断收敛到统一授权服务；
- 为当前 `admin/member` 数据提供无损迁移。

### P2：管理视图与聚合事实

- 按授权组织子树聚合项目、运行、交付、用量和风险；
- 上线待我决定、异常下钻和结果追溯；
- 员工对话、敏感材料和凭据保持最小可见。

### P3：委派、审批与 Agent 治理

- 预算分配、权限申请、高风险动作和发布审批；
- 按组织管理可用 Agent、Skill、工具与执行器；
- 委派不超权，撤销可传播，历史任务保留当时权限快照。

## 12. 首版不做

- 不一次实现完整 IAM 产品；
- 不允许模型自行提权或以自然语言覆盖硬策略；
- 不将聊天记录、在线时长、代码行数变成员工绩效监控；
- 不因领导需要报表而伪造 ROI 或“节省工时”；
- 不先开发大而全的组织管理页，再补服务端授权；
- 不把不同 Agent 的提示词协作当成企业权限。

## 13. 成功标志

当一名部门负责人登录后，可以在不阅读每个员工对话、不懂底层 Agent 的前提下，于一个页面回答以下问题，本方向才算成立：

> 我的团队在做什么，产出了什么，哪里有风险，花了多少，现在有什么事必须由我决定？
