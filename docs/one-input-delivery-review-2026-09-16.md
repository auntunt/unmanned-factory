# 从一次输入到可用产品：使用流程与职能体装载审查

日期：2026-09-16。范围：当前工作区 webuddy 源码、相关历史验收记录，以及本地原始逆向 Skill ZIP 的只读结构检查。本次是优化分析，不是功能实现或线上部署验收。

## 1. 结论

当前产品把平台的内部对象和操作责任过多地交给了使用者：项目、职能体、模块、规格、运行、适配、维护草稿、清单、发布。用户想委托一个结果，界面却要求用户理解并串联这些对象。

目标应改为：用户描述目标并附上已有材料，平台自动准备工作区、形成可检验规格、选择已就绪能力、实现、验证、修复和打包；同一条任务里拿到可运行成果。用户不必选择模型、工作类型或 Skill，也不应负责判断该“继续”“重试”还是“重新分析”。

一次输入是默认交互目标，不是对任意模糊需求的无条件成功承诺。可逆、低风险的设计和实现细节由系统采用合理默认值并记录；缺少必须的样本、访问权限或决定性业务规则时才集中提问。问题解决后接续原任务。

## 2. 对所附 brief 的判断

附件针对另一个目录中的旧 `web/src`、`factory/api.py` 和 `factory console`。当前项目采用 `frontend/src`、`factory/control` 与 `factory-web`，README 已明确旧控制室 HTTP 服务移除。不能把附件中的文件修改清单当作当前仓库实施指令。

值得保留：状态来源一致、失败有出口、提交与成果关联、重启不丢记录、不把未知值显示为零。

不作为这次的主要路线：增加待确认导航、重排阶段条、增加解释气泡。这些改善观察和理解，却没有减少用户必须作出的决定。若默认仍然暂停等待用户确认，再精致的阶段展示也无法实现一次输入。

## 3. 源码中可确认的断点

| 断点 | 当前证据 | 影响 | 建议 |
|---|---|---|---|

已有连续执行、独立验证、自动修复、持久队列和版本冻结值得保留。此次不是重新制造一套 agent 框架，而是让现有能力完成一条不中断的委托链。

## 4. 逆向职能体：为什么“部署和加载”一直不像完成了

### 4.1 已有历史故障，不等于当前在线状态

`docs/ui-audit-2026-09-16.md` 记录：当次线上检查逆向工程岗位清单为零项，外部资料已保存，但适配遇到上游 504，尚未成为可用 skill。

因此至少在该次检查时，问题发生在正式启用之前。后续提交增加了临时错误重试、分片进度恢复和围栏 JSON 解析兼容。这些修补不能证明历史草稿已续跑成功、已签署、已挂载，更不能证明转换业务已通过验收。本次未重新读取线上运行状态。

### 4.2 原始 ZIP 本身可以被当前检查器接受

只读检查 `/Users/auntlee/Downloads/project-maintenance-skill.zip`：

- SHA-256：`ace6028c7b49aa782362110999e3ce3c1a1f9be2c61260edebd6aaf43ae236f7`，与原维护方案记录一致。
- 共 8 个文件：1 个 SKILL.md、5 个 references Markdown、2 个 Python 脚本。
- 当前 inspect_skill 接受该包。包内 references 和 scripts 路径使用反斜杠；不能仅凭这一点断言上传失败。
- 按当前统一 abilities 接口分流条件，这个包会走“维护附件”通道，上传本身不会自动启动适配或完成维护应用。历史线上使用的外部包与入口仍须对照运行记录，不假定就是此包。

### 4.3 “就绪”至少跨越四个层次

1. **资料保存**：原文件、来源与哈希存在。
2. **方法生效**：维护版本或已签署清单中包含所需方法。
3. **实际装载**：任务冻结了正确版本，正文及引用资料在执行上下文中可读。
4. **业务可用**：需要的工具和平台环境可用，真实样例能够得到经过检查的输出。

当前 UI 和流程虽已区分附件、草稿和装备数量，但尚不能用“上传成功”或“适配通过”代表第 4 层。签署适配结果的实质是保存方法和映射，不是完成软件安装。

### 4.4 优先复现的装载疑点：入口有了，references 未必可读

源码中两条路径不对称：

- `skill_ingestion_runs.py` 的 sign 将原 ZIP 存入 skill_assets，把入口正文写成模块并加入 manifest；新建配置没有同步把原附件加入 version.skill_ids。
- `agent_manifests.py` 的 freeze 将所选模块正文编译进 instructions。
- `mounts.py` 的 compile_mounts 按 agent_snapshot.skill_ids 读取附件里的 Markdown／文本；未看到按 manifest_skills.external_source.asset_id 自动补齐引用文档的路径。

这意味着适配后的入口正文能进入模型，不代表其相对 references 已成为可读取资料。已有项目数据源可能提供这些内容，因此这里是源码识别出的高优先级缺口，不能直接断言某次生产任务必然失败。

建议补一条独立装载验证：签署一个入口引用 references 的小包，创建真实任务，确认执行者能按引用读到正文并核对哈希；导出、重新导入后再验证一次。只断言“模块数量为 1”不够。

修复方向是按冻结包建立规范化引用索引，按需读取所选能力及其引用闭包；保留原路径与哈希。不能把整包粗暴塞进提示词：现有挂载有单文档 40 KB、总量 200 KB 限制，清单还有 24 项和编译 10 万字符限制。

### 4.5 工具环境仍是独立缺口

当前外部摄取不执行包内脚本、不自动安装工具；宿主 shell 入口标 unsupported，依赖作为前置条件记录。原逆向包还涉及 Ghidra 专用脚本和平台依赖。保存 Python 文件不会让 Ghidra API、Windows 环境或参考软件自动出现。

建议维护侧建立可验证的环境准备步骤：依赖识别 → 对应执行环境探测 → 允许范围内安装和连接 → 最小工具试跑 → 真实样例验收。包内任意脚本不能因被上传就自动执行；通用依赖可通过平台维护的安装配方准备。

原方案指出该岗位实际业务为格式转换。应提供“格式分析与转换维护”的默认方法集合，按任务取用；不要因一个宽泛入口混合了不同专业内容，就让普通转换任务加载全部方法或反复处理无关授权。共享身份和权限变更仍保留独立记录。

## 5. 推荐的默认体验

主界面只提供一个目标输入框、附件入口和“开始制作”。已有项目从当前上下文继承；无项目时自动建立工作区。项目名、技术栈、工作类型、模型和方法模块均由系统确定，用户可在设置中覆盖，但不成为提交前提。

提交后的同一页显示：

- 用户原始目标，以及一句当前进展。
- 必须由用户补充的问题；没有问题就不出现此区域。
- 完成后的实际预览、下载文件、使用说明及验收摘要。

日常导航收敛到“开始制作”和“我的作品”；模型配置、团队、用量、职能体维护和详细运行记录放进管理入口。执行期间主要操作是补充要求和停止；故障恢复动作由后台依据检查点选择。

平台内部仍保留：原始输入 → 自动规格与可见假设 → 任务所需能力冻结 → 连续编码 → 构建与真实交互检查 → 独立验收 → 有限自动修复 → 打包与可访问预览。

自动规格不能变成自动扩权。部署到已有生产环境、发布到外部账号等动作仍依据用户已有授权和项目策略执行；普通预览与成果打包不应因此被阻断。

## 6. 质量来自交付证据，而不是更多选择框

“可用 coding 产品”的默认完成条件应包含：

| 交付类型 | 必要证据 |
|---|---|
| Web 产品 | 从干净环境构建成功；可访问预览；主业务路径真实操作通过；必要的空态和错误态；用户可读的运行说明 |
| 有视觉要求的页面 | 对目标页面逐项检查布局、内容与交互，并关联本次实际截图；无参考材料时明确采用的是设计目标，不声称像素复刻 |
| 格式转换工具 | 固定输入样本与预期输出；字段、数量、单位和关系检查；异常输入处理；可运行命令或安装包 |
| 旧项目修改 | 原有关键行为不回归；新增需求通过；启动和回滚方式明确 |

不同产品按实际业务生成检查，不强迫所有任务都做 Web 预览。构建通过不能替代业务验收，源码 ZIP 不能冒充已构建安装包，模型总结不能替代实际检查输出。

首次提交时保留原始目标，自动规格补足细节但不能偷偷缩小目标。独立验证覆盖原始目标与冻结规格。可修复的失败自动回到当前实现现场；环境故障恢复环境，不能误触发从头重写。

## 7. 建议实施顺序

**第一批：先打通两条闭环。**

一条是普通编码：一次提交，自动准备工作区和规格，自动执行、验证、修复，返回可运行产物。另一条是职能体准备：一次上传，自动衔接准备流程；系统能说明当前是否可装载、缺什么环境，并实际完成一个格式转换样例。复用现有运行存储与恢复机制，不新增一套平行调度器。

**第二批：收敛 UI。**

移除普通入口的工作类型、Skill、模型和阶段确认选择；职能体维护页面与任务页面分离；统一故障继续入口。不能只把必填配置折叠起来，让用户运行到一半再被迫回来找。

**第三批：验证质量和稳定性。**

选取代表任务：简单网站、带数据交互的小应用、现有项目修复、真实格式转换。记录一次交付成功率、提交后人工干预次数、用户到首个可运行成果的时间、自动修复成功率、预览和安装包可用性。保持同一批输入与验收条件，与现有流程对照，不以按钮减少或单测通过代替产品质量提升。

验收还应包括：准备过程遇到 504 后接续原记录；服务重启后接续任务；能力引用文档可读；工具缺失时准确定位；同一个包重复上传不产生一串难以辨认的草稿。普通低风险样例目标为一次提交、无额外决策；无法恢复时明确保留成果和缺失条件。
