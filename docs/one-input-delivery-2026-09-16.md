# 一次输入制作与职能体资料装载

本次把默认首页改为目标输入与可选附件：自动建立工作区、提交任务、形成规格并进入编码与独立验收。原项目入口仍支持直接提交；工作类型、发布等选项归入高级操作。主导航保留“开始制作”和“我的作品”，详细记录与配置放在“管理”。职能体页面仅在维护模式展示装备、清单和进化设置。

## 自动规格的边界

新入口向 `/api/v2/runs` 提交 `interaction_mode: automatic`。该选择冻结在本次运行的 source 中，纳入幂等指纹，并以 `spec.auto_confirmed` 和 `policy: submission` 记录。它不修改项目设置、不授予部署或受保护能力权限，也不跳过独立验收。旧 API 未传该字段时仍兼容原先的 review 行为；已有项目的自动规格策略仍有效。

分析对可逆实现细节采用默认值并记录假设，必须保留原始目标和具体可验收流程。原需求、规格与版本引用继续被冻结。提交失败后，当前页面复用已创建工作区和同一提交键，不重新建项目。

## 能力准备与装载

- 单 Skill 与多 Skill ZIP 都自动进入已有的持久准备和独立验收流程，不再要求单包上传后另开维护会话。
- 同包重传复用进行中或可恢复记录；已取消、失败的终态允许重新准备。
- 上传前与运行前使用同一零工具配置检查，避免开始后才发现适配供应商不兼容。
- 接受一个完整 JSON 围栏前后的普通说明；说明不进入映射。格式或映射错误最多自动纠正一次，连续失败不保存无效结果，也不自动启用。
- 维护侧默认展示 ZIP 上传，其余来源、映射编辑收起；权限与共享能力签署保留。
- 修复 Windows 路径下的 Skill 识别。
- 所选外部能力的入口和显式相对 Markdown／文本引用递归装载，校验归属、来源与正文哈希；不会直接加载整个能力库。
- 职能包导入重映射附件 ID，保留来源哈希关系，解决导出再导入后引用资料断开。

准备通过代表映射和资料准备完成，不代表 Ghidra、Windows 或外部软件环境已验收。脚本和二进制不因上传自动执行。当前引用读取仍沿用 Claude 工具能力，40 KB 单文档与 200 KB 总挂载限制保留。

## 验证方式

覆盖一次提交、自动规格审计、幂等重试、完整交付与预算接续、真实适配签署后的引用读取、清洗 ZIP 哈希、导入导出、归属与大小限制、取消后重传，以及前端工作/维护模式分离。浏览器演练使用明确隔离的脚本执行器，不能替代真实模型与业务样本验收。

前端最终全量 242 项与构建通过。后端全量执行为 2149 passed、20 skipped、2 deselected，唯一失败来自临时浏览器验收脚本位于 ignored 源码目录；脚本移出后该文件 13 项通过。随后最终改动相关 144 项通过；内层 ZIP 清理补丁另经 75 项关联回归通过。完整全量未因临时脚本位置再重复执行，以上范围分别记录，不将专项结果冒充重新全量通过。

浏览器已走通同一次输入到 ZIP 下载，包含自动规格与真实文件内容核对；截图与执行器边界见 [浏览器验收](design/one-input-2026-09-16/verification.md)。

部署现场核实为 `factory-web.service`、`/home/ubuntu/workspace/unmanned-factory`，实际服务运行独立目录 `/home/ubuntu/releases/factory/<revision>`；旧部署文档中的无连字符名称不适用于当前机器。保持现有外部环境文件、数据目录和 Caddy，使用独立版本目录切换与回退。

## 真实模型验收追加修复

首轮线上 CSV 转换器运行生成了源码并独立执行 26 项测试，但暴露三个协议兼容问题：事前声明附带普通说明时被忽略、验收返回 `acceptance_coverage` 别名时证据未入账、旧生成器的 `## expanded` 标题被误算入原始需求。

现在接受标准助理消息内唯一完整声明前后的说明，继续在收到声明时核对修改时序；验收别名使用相同的逐项校验，冲突字段不通过；规格解析兼容旧标题，新生成统一 `## expanded spec`。真正改写原始需求、事后补声明、伪造能力引用仍被拒绝。缺项才补询验收，明确失败不进行无谓的证据补询。

线上历史内容只读回放确认原始需求未变，20 条模型证据均有效；没有追认旧声明，也没有修改旧运行状态。追加关联回归 91 项通过、2 项跳过。
