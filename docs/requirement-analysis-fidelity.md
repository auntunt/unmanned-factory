# 需求分析职能体与保真验收

通用编码的默认链路变为：原始需求 → 需求分析 → 一次规格确认（含 skill 与保真标尺）→ 既有规划、编码、独立验收和交付。维护工作流默认保持原样，可在提交时选择加入需求分析。

## 单次确认与冻结

`general` 的新提交必须先进入 `requirement_analysis`，产出 `spec_draft`（目标、屏页、流程、数据、非目标、风险假设）、带理由的 `recommended_skills` 和可选 `fidelity_target`。模型仅提出规格；平台校验页面与版本引用，不允许虚构 skill 或更改权限。

“需求分析”是内置岗位，首次使用时登记到职能体库，运行保留其版本快照。匹配目录由已就绪能力模块和职能体引用关系组成。无匹配时显式展示没有推荐，不能伪造挂载。来源版本与正文在分析时冻结，勾选后只影响本次运行，不改变项目长期绑定。

每次运行拥有独立 Git 分支与工作区，草案写入 `.spec/requirements/<run_id>/spec.md` 的 `raw source`。未确认时为 `draft`，明确标注“尚未人签”；确认后为 `active`。确认时不改项目基线，不影响其他运行。首次 GitHub 上传后，只有原项目基线仍未变化且工作区干净，才沿用既有快进同步；规格分支保留原始基线用于这一核对。规格随最终代码交付，既有规格格式不变。原始需求与确认草案均保留；独立验收机械检查 raw source 未被 worker 改写。

`awaiting_spec_confirmation` 界面同屏编辑规格、勾选 skill、调整逐屏保真标尺。开工、编辑后开工、放行都记录同一确认与当前选项，随后自动批准既有计划；放行不会跳过验收，也不授予任何远程、目标或敏感工具权限。运行故障沿用 `needs_human`。

项目设置 `auto_spec_confirm` 默认关闭；管理员显式开启后，默认采纳建议项，并记录 `spec.auto_confirmed` 与对应项目 revision。项目设置保留乐观锁和审计。确认接口保留 CSRF；成员只能确认自己在已分配项目内发起的运行。

## 保真证据

只有存在参照目标的任务生成 `fidelity:` 验收项。每个页面的布局、配色、组件、交互逐条进入 acceptance ledger，与功能验收同级。规格中的目标、页面、流程、数据模型和非目标也单独成为验收标准。

独立验证员使用既有 project-browser 打开本机预览，执行交互、截图并读取图片，逐条输出 like/unlike 和具体说明。平台把其引用的截图路径解析为本轮验证的真实事件与归档截图；不存在、旧轮次或非独立验证员的截图不能支持通过。明确 unlike 是可修复的功能性 fail，连续执行时沿用现有的一次自动修复与复验；人工续跑同样回到编码修复，不能误当环境异常只重跑验收。环境缺失、缺少截图或无法判断是 unverified，不能当作已通过。

不自动抓取外部产品。标尺来自模型已有知识与用户提供信息，必须明示依据和假设；这不是与外站原始截图作像素级比较。输出质量提升仍需真实任务对照验证，不能凭新增阶段宣称已经优于裸 Claude Code。

## 预算与续跑

需求分析使用独立费用记录（默认不设美元停止线，仅监测；可显式设置独立预算），费用仍计入总用量及团队额度，但不扣减编码与验收的运行预算。显式设置预算时，未知费用保留上限占用，不当作免费。

预算暂停可用“续跑并进入下一阶段”：明确按项目当前额度增加本次运行可用预算，历史费用和事件保留。恢复沿用既有 checkpoint 判断；有已验证任务与提交时直接恢复验收，未完成实现时继续编码，不能为跳过步骤而伪造完成。团队 token 闸门、原授权、并发限制和恢复基线核对继续生效。

## “丑团”复盘（生产只读记录核对）

核对运行 `552ffbfc91b140f7bb4f4d36d2b1723d`：需求明确要求模拟购物、按美团界面呈现、点单与呼叫骑手、不实际收货，并要求完全理解后执行。

- **需求未完善**：没有单独保存并确认屏页、布局和交互规格，规格树未启用。实际验收标准只有一项“完成用户要求，并用实际运行或功能检查证明结果可用”。
- **零 skill 挂载**：`module_snapshot` 数量为 0，`mount_snapshot.modules=[]`，也没有冻结职能体。系统缺少需求驱动的方法建议与选择环节。
- **缺少“像”的独立验收**：不能简单说“只检查能启动”。现有记录确实检查了构建、浏览商品、购物车、结账、订单流转及模拟呼叫骑手，并报告无浏览器错误。但 ledger 只有 1 项 pass，没有逐屏视觉标准、like/unlike 判断或相应截图证据要求。“Meituan-style”只是模型综合结论中的陈述。

本轮分别用规格确认、建议 skill 冻结和逐屏保真 ledger 对应这三处缺口，不改写该历史运行，也不把历史结论追认成新的保真验收。

## 验证与兼容边界

- 本地后端全量 `pytest -m 'not smoke'`：2080 passed、20 skipped、2 deselected。新增 18 项需求分析测试包含完整交付、一次确认、冻结引用、保真不符与缺证据、授权/CSRF、预算隔离及验收续跑不重跑编码。首次分析暂停的修订号 0 续跑另有 HTTP 回归用例，补丁与路由契约合计 21 项检查通过。
- 需求分析与 GitHub 发布链路另有 34 项联合回归通过，覆盖确认规格后的首次发布基线推进。保真失败与续跑阶段分类另有 36 项联合回归通过。
- 前端 `npm run build` 与 213 项 vitest 通过。浏览器隔离 fixture 验证单表单、一次提交、亮暗主题和手机宽度；截图与报告位于 [需求确认界面记录](design/requirements-2026-09-15/verification.json)。这些界面 fixture 不代表真实模型的视觉评判准确率。
- 旧执行器回归用例显式使用维护 operation 保留原断言；新的 HTTP 默认 general 单独验证确认门。内部“生成规格树”运行标记为 `spec_bootstrap`，继续其现有维护流程，不被误认成用户新建通用编码需求。
- 连续执行的风险和模型选择使用可核验的原始提交意图，平台维护预设不会仅因含“权限/授权”说明触发高风险。原始文本与编译文本摘要绑定；后续改写的需求不能被旧输入覆盖，模型生成的任务风险仍完整检查。
- 不修改历史已交付运行，不安装外部工具或抓取产品，不增加编码执行器。新规格文件与原始数据仍由既有工作区、Git、证据和权限体系管理。


## 2026-09-15 预算边界修补

需求分析使用独立 `requirement_analysis` profile，默认 Claude `sonnet`，不继承 planner 模型。可通过服务环境 `FACTORY_REQUIREMENT_ANALYSIS_PROVIDER` / `FACTORY_REQUIREMENT_ANALYSIS_MODEL` 指定账户支持的供应商与模型 ID（默认 `claude` / `sonnet`）；每次调用事件记录实际 profile 与模型。项目设置中分析预算留空表示仅监测，已有显式额度不自动覆盖。

预算错误携带已收到的正文与用量跨 SDK 子进程返回。只有 `budget_exhausted` 且正文通过完整 Analysis 校验时，保留草案进入确认；不完整 JSON、非法 skill 引用或其他错误仍暂停。费用照实保留，不因救回清零。取消检查与自动确认策略保持生效。

需求分析暂停的「追加额度并重新分析」和继续接口给分析追加当前分析额度，重跑分析，随后仍进入规格确认，不跳到规划/编码。编码与验收的续跑仍使用原 checkpoint 规则。

项目编码预算默认留空、仅监测。按人管理可使用团队页已有的成员月度 token 额度；项目美元费用用于观察，不必另设项目停止线。成员额度、供应商余额与美元费用是不同计量，不能互相换算。
