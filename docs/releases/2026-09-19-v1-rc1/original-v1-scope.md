# 首版范围与验收

## 产品成立的三个条件

1. 一个负责人可以用提示词完成软件开发和交付，其他人可以体验成果并反馈。
2. 工作进行中，负责人知道在做什么、结果在哪里，并能让新要求真实进入后续执行。
3. 团队自己开发的 CLI 工具可以独立使用，也可以由管理员或组长挂靠到团队职能体，成员通过对话和材料获得结果。

第三项是主线产物的复用闭环，不将 webuddy 改造成通用助手商城。所有能力不必采用同一个执行循环。

## 首版必需

下表是目标验收标准，不是当前通过情况。具体提交、测试命令、运行 ID 和证据路径须由实施报告补齐。

| 编号 | 范围 | 最小验收方式 |
|---|---|---|
| V1-01 | 单一入口与连续任务 | 一次输入真实开发需求，保存后刷新仍能恢复任务、进度、消息和成果；不要求依次创建需求、项目、运行 |
| V1-02 | 成熟 Coding 执行器 | 至少一个经过真实验证的 Codex 或 Claude Code 配置完成文件修改、命令执行与测试；未验证的备用执行器不显示可用 |
| V1-03 | 真实交付 | SaaS 保存对应代码提交、测试记录、部署结果与固定公司测试地址；打开地址实际执行一个核心业务操作 |
| V1-04 | 同任务修改 | 输入修改要求，保留前一轮成果和记录；完成新一轮测试、GitHub 同步及同地址更新，能辨认地址当前对应的版本 |
| V1-05 | 人的干预 | 运行中补充不会丢失；显示已记录、待应用或已应用；重试不重复消费；停止显示请求和实际结束状态 |
| V1-06 | 轻量交付分支 | 交付描述能区分服务、安装包、CLI；不适用的部署步骤不显示为失败，也不能把源码 ZIP 当成安装包 |
| V1-07 | 团队定制工具 | 一个真实 CLI 在平台外可运行；同一版本包验证后挂靠角色，成员上传支持的材料得到可下载结果；卸载挂靠后不再用于新任务 |
| V1-08 | 日常角色使用 | 报价、总结等沿用无项目聊天；工具调用有真实回执，不自动新建 Coding 工程；刷新能恢复结果 |
| V1-09 | 可观测与恢复 | 失败说明步骤、原因和已有成果；日志可展开；重试不重复创建外部资源；无法确认外部动作结果时显示待核对 |
| V1-10 | 统一界面 | 开始制作、历史、职能体、工程总览和设置共用 AppShell；桌面及手机无第二套导航、无输入框遮挡 |

V1-06 的首版验证至少覆盖 SaaS 与一个独立 CLI。安装包的目标 OS、打包工具链和安装验证是待选择的交付配置：在选择并完成实测之前，保留产品方向和接口位置，不将“完整支持所有安装包”写进首版完成声明。若首批正式交付选安装包，则必须补该目标系统的真实安装、启动、卸载验证。

## 已有环境的一次配置

管理员集中配置执行器、GitHub 凭据引用、公司测试服务器与项目固定地址。任务继承已授权配置，用户无需逐次选模型、服务器或重复点审批。项目目标不明确时只澄清必要信息。

公司域名接入首版允许使用已配置的域名或子域名映射；新增记录按已有公司 DNS 条件采用简单模板或一次人工配置。不建设域名购买平台，不要求先接完所有 DNS 服务商。飞书已有通知继续保留；正式交付记录可在主闭环通过后复用现有连接补充，不阻塞首个产品体验。

## 后置，只保留设计位置

蓝绿、每版本测试域名、正式邀请与签收流程、多开发者并行编辑、复杂 group 编排、审批中心、语音客户沟通、商城计费、全自动模型竞价或自学习路由、跨执行器无损迁移、独立监控大屏、完整深色主题细化。

已有这些方向的可用代码不因收敛范围而删除；不新增建设，也不抢占首版主线。隔离、凭据边界和正确终态属于已有工具可用性的底线，与企业审批治理不同；不得为了赶进度把任意 CLI 放进服务主进程执行。

## 三条演示及失败验证

**A 软件主线：**预约管理小系统，完成一项真实新增/编辑操作；GitHub 可追溯，固定测试地址可访问；输入“新增筛选条件”后同地址更新。保存两轮版本与验证证据。

**B 定制工具：**优先复用已存在的 CSV 工程量清单 → XML 包证明独立 CLI、发布、团队挂靠和日常调用。再更换输入文件验证没有写死样本。MFD 和公司 PPT 作为后续业务实现，不混入平台通过结论。

**C 人在场：**运行中补充要求，上翻日志、刷新页面，要求仍可追踪；在不具备在线追加能力时安全衔接下一步。测试失败、部署失败、工具输入错误各至少一个实际失败场景，页面不冒充完成。

三个演示共同验证产品闭环；不要求穷举所有工具、模型或所有操作系统。
