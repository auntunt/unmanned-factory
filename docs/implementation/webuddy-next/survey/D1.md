## 部分实现 / 需要修复

### 4. 非 general 操作缺少 delivery_type 推导写入

- `delivery_type_inferred` 仅在 `factory/control/requirement_analysis.py:298-304` 的 `confirm()` 中写入。
- `confirm()` 仅在需求分析流程走完 `awaiting_spec_confirmation` 时触发。
- 非 general 操作（bugfix / release / startup / dependencies）在 `run_routes.py:88-130` 的 `new_run()` 中不经过需求分析，直接 `svc.start_plan()`，**不写 `delivery_type_inferred`**。
- `derive_delivery_type()` (`deliverables.py:218-236`) 的回退路径：`artifacts.delivery_type`（显式声明，极少使用）→ `run.delivery_type_inferred`（此处缺失）→ 根据 items 中有无 installer 文件推断。
- 后果：bugfix 等运行的 `delivery_type` 始终为 `null`，前端显示「未声明」。

**最小修复落点：** `run_routes.py` `new_run()` 在 `store.create_run()` 之后、`start_plan()` 之前调用 `infer_delivery_type_from_text(body.request)` 并写入 `delivery_type_inferred`。或在 `start_plan()` 入口统一补推导。

### 5. 「已加载 Skill / 已调用工具」展示 — 部分实现，缺专用 UI

**数据来源（后端）：**

- `tool.call` 事件在 `factory/control/providers.py:445,745,863-893` 由 provider worker 实时 emit，持久化到 events 表。payload 含 `{id, name, command/changes/…}`。
- `provider.configuration` 事件（`providers.py:686`）记录模型 / provider 配置。
- `execution.environment` 事件记录执行环境信息。
- Events API `run_routes.py:267-270` 不做类型过滤，全量返回 `tool.call`、`provider.configuration` 等所有事件。

**前端消费：**

- `ExecutionLog.tsx:7` 用正则 `/command|tool/i` 匹配 event type 并分类为「命令」样式，但 **不按工具名聚合**、**不单独列出 skill 名**。它是一个时间线滚动日志，不是工具/skill 摘要面板。
- `EventsPanel` (`RunPage.tsx:292-296`) 以原始事件列表展示，`eventTypeLabels` 映射仅有 4 种类型，`tool.call` 会直接以原始 type 字符串显示，无专门翻译或聚合。
- 没有任何组件提取 `tool.call` 事件做「已调用工具列表」或「已加载 skill 列表」的摘要视图。

**Skill 记录（manifest 级别）：**

- `AgentManifest.tsx:24-29` 展示职能体岗位清单中「引用的 skill」，但这是 **配置级**（agent manifest 的 skills 引用列表），不是运行级记录。
- `CapabilitySources` (`capability-links.tsx:14-17`) 展示能力的来源运行链接，不是运行加载了哪些 skill。
- 运行详情的 `FrozenRuntime` 组件（`RunPage.tsx:214-222`）展示模型配置快照，但不含 skill 列表。

**空态诚实性：**

- `ExecutionLog.tsx:25` 空态显示 `'尚无已记录事件，等待下次同步。'`——诚实。
- `EventsPanel` (`RunPage.tsx:295`) 空态显示 `'运行尚未产生可展示的持久化事件。'`——诚实。
- 但因为根本没有 skill/tool 摘要面板，"缺记录时显示缺记录"这条要求在 UI 上无从体现。

**判定：期望 3 部分实现。运行级 `tool.call` 数据已有真实记录（非硬编码），通过原始事件流可见，但缺少「实际加载的 Skill」和「实际调用的工具」的摘要 UI。**

### 6. 「继续修改」成果 — 部分实现

- 运行详情的执行视图（`RunPage.tsx:427`）提供恢复执行入口：`act('continue')` 发 POST `/api/v2/runs/{rid}/continue`，以及 `retry()` 发 POST `/api/v3/runs/{rid}/retry`。
- 但入口在执行视图 (`activeView === 'execution'`)，不在交付视图 (`activeView === 'delivery'`)。用户在成果页看到文件后，无法直接从成果页发起针对该成果的后续 run。
- 交付视图的操作仅有：下载 ZIP、GitHub 发布、能力归档（distill）。

**判定：从执行视图可继续/重试已有 run，但成果页本身无「继续修改」入口。**

## 缺失（需要新增）

### 7. Skill/Tool 摘要面板（影响期望 3）

- 需要一个运行级的 UI 组件，从 events 表中的 `tool.call` 事件聚合出「已调用工具」列表（tool name + 调用次数 + 成功/失败），从 `modules.frozen` / `mounts.frozen` 事件（如存在）或 `agent_snapshot.manifest_skills` 提取「实际装载 Skill」列表。
- 无记录时应明确显示「本次运行未记录 skill / 工具调用信息」，不留空白。

### 8. 成果页「继续修改」入口（影响期望 1）

- Deliverables 组件中缺少一个按钮，允许用户基于当前成果的 run 直接提交后续需求（followup）或创建 retry run。现有 followup 机制（`/api/v2/runs/{rid}/followup`，`RunPage.tsx:63-74`）技术上可用，但没有在成果页暴露。

## 不确定 / 需要主会话裁决

- `tool.call` 事件 payload 中的 `name` 字段是否足以区分「工具」与「skill」？当前 `name` 值形如 `command`、`file_change`、`Write`、`Bash` 等，是工具名而非 skill 名。Skill 加载记录可能需要依赖 `modules.frozen` 或 `mounts.frozen` 事件。
- 「继续修改」的产品定义：是在原 run 上 followup，还是创建新 run 并关联原成果？前者已有 API，后者没有。
