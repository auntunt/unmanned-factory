# D2 Skill 与工具区分 / Skill 会话级导入 — 现状调查（只读，基线 6fe1883）

## 现有对象模型

| 代码对象 | 存储 | 对应产品概念 | 说明 |
|---|---|---|---|
| `instruction_modules`（ModuleStore） | SQLite `instruction_modules(id,version,data)` 不可变追加 | **职能体** (Skill) — 方法、知识、垂直指导 | 分 style/knowledge/workflow/delivery 四类，版本化不可删，按项目搭配冻结进运行 |
| `agents` + `agent_versions` + `agent_manifests` | SQLite 三表 | **职能体**的岗位容器 | 一个 agent 拥有 identity + 引用多个 instruction_module（SkillRef[]），由清单 manifest 编排 |
| `capability_packs`（PackDetail） | SQLite + 文件 | **职能智能体** — 可独立运行的工具 | 有 entrypoint、runtime、tool contract、独立验证 cases、环境检查；主操作是 validate/publish/invoke |
| `capabilities`（v3 Capability） | SQLite `capabilities` 表 | 沉淀能力 — 运行中提炼出的经验方法 | 可从项目开始（invoke），绑定项目+版本 |
| `skill_assets` | SQLite `skill_assets(id,agent_id,data,content,created_at)` 不可变 | 已上传附件 / 外部 ZIP 归档 | 人签后原包保存于此 |
| `skill_ingestions` | SQLite `skill_ingestions(id,project_id,package,data)` | 外部 skill 包的导入草稿 | 从 ZIP/目录进入，经适配+独立验收+人签后 → agent manifest + instruction_modules |

**产品映射总结**：
- "职能体"（Skill / 方法知识）→ 代码 `instruction_modules` + `agent` + `agent_manifests`
- "职能智能体"（可独立运行的工具）→ 代码 `capability_packs`（PackDetail）
- 两者共同出现在 **能力中心**（`/ability-center`）的三个 tab 中：方法模块 / 沉淀能力 / 职能包

## 已实现（可复用）

### E1. 三入口分列不同类型

能力中心 `CapabilityCenter.tsx:15-26` 用三个 tab 分列：
- **方法模块**（`ModulesPage`）→ instruction_modules
- **沉淀能力**（`CapabilitiesPage`）→ v3 capabilities
- **职能包**（PacksPage → `PackDetail`）→ capability_packs

三者页面结构已分化。方法模块展示 instructions/description/category；职能包展示 entrypoint/runtime/support_matrix/evaluations。→ **两类内容已有不同页面结构**。

### E2. Capability Pack 的主操作是"使用工具"

PackDetail.tsx:39-211：主操作为 **运行验证**（`validate`）和 **发布版本**（`publish`），对应产品概念"提供输入并使用"。职能包详情展示调用入口、依赖锁、验证 case、环境状态。→ 已区分于方法模块的"搭配/添加"动作。

### E3. 模块的主操作是"搭配/添加"

ModulesPage.tsx:96 的 button 文本为"已添加" / "添加"；63-69 的保存操作是 `save`（保存组合到项目）。AgentManifest.tsx:29-30 中加入 skill 的操作是"加入 skill" / "移除" / "采用最新版本"。→ 动词区分部分存在。

### E4. 外部 ZIP 导入已实现完整流程

- 前端入口：`SkillIngestion.tsx`（项目范围）+ `AddAgentAbility.tsx`（职能体范围）
- 后端：`skill_ingestion_routes.py` 提供 `POST /api/v4/skill-ingestions`（ZIP）和 `/directory`（挂载目录），两者均经过 `read_package` 解析和 `directory_zip` 封装
- 存储：`skill_ingestions` 表保存原包 BLOB 和元数据 JSON
- 来源版本追踪：`source_sha256` 记录原始 ZIP 的 SHA256（`skill_ingestion_runs.py:78,125-127`），每个 skill 的 `external_source` 保存包 SHA256 + 路径 SHA256 + 正文 SHA256 + ingestion_id + asset_id（`skill_ingestion_runs.py:125-127`）

### E5. 签署后不自动发布到团队

`skill_ingestion_runs.py:139`：`active_refs` 仅含人签选中的 skill，追加到目标 agent 的 manifest。
`modules.py:84-85`：`owner_agent_id` 标记的模块在全局 list 时被过滤（`not m.get('owner_agent_id') or m['owner_agent_id'] == agent_id`）。→ 岗位专属模块不进入其他项目/职能体的模块库。

### E6. 授权标记逐项人签，不自动扩大

`skill_ingestion_runs.py:101-104`：签署时验证 authorization dict 与 mapping 中 skills 的路径集合完全一致，且每个值是 bool。
`SkillTargetAuthorization.tsx:19`：运行级目标授权仅限当前 run，不转移到新 run。

## 部分实现 / 需要修复

### P1. 动词未统一："加载" vs "搭配/添加/装备" 混用

| 位置 | 用词 | 产品要求 |
|---|---|---|
| AgentManifest.tsx:25 | `"skill 是工具，职能体是岗位"` | 这句话本身与产品定义冲突——产品说 skill 是方法/知识，不是工具 |
| AgentManifest.tsx:29 | `"已装备能力"` / `"引用的 skill"` | 产品要求 Skill 的动作是"**加载**" |
| ModulesPage.tsx:96 | `"已添加"` / `"添加"` | 应为"搭配"或"加载" |
| CapabilitiesPage.tsx:102 | `"开始一项工作"` | OK，capability 的 invoke 语义正确 |
| AddAgentAbility.tsx:51 | `"为职能体添加能力"` | 应区分加载 skill 与安装工具 |

→ 文案层面 Skill 与 Tool 的动词尚未对齐。产品文档 `capability-terminology-alignment.md` §2 明确要求 "Skill 主操作为加载到当前会话；工具主操作为使用/调用"，代码中没有出现"加载"这个动词。

### P2. Pack 的标题仍叫"职能包"，与产品"职能智能体"概念有偏差

PackDetail.tsx:39 注释 `"职能包详情"`，Tab 标签 `"职能包"`（CapabilityCenter.tsx:26），详情头 `"职能包"` 各处。产品文档区分"职能体"（方法）和"职能智能体"（可独立运行的工具），"职能包"是一个中间概念（导出/导入单位），不等于"职能智能体"。→ 标签需要对齐但不需要重命名代码对象。

### P3. 能力中心（/ability-center）没有对 Skill 和 Tool 做类型列标注

CapabilityCenter.tsx:26 三个 tab 标签为"方法模块 / 沉淀能力 / 职能包"，但没有任何地方标注"这是 Skill（方法知识）"还是"这是独立工具"。设计文档 §2 B01 要求"显示明确类型"。→ 类型标签缺失。

### P4. GitHub 来源导入：仅 Webhook 方向，无主动拉取

`webhook_routes.py:13-75`：有 GitHub webhook 接收 issue 创建 run 的逻辑；但没有 `POST /api/v4/skill-ingestions` 支持 GitHub URL 作为来源。前端 `SkillIngestion.tsx` 只支持本地 ZIP + 挂载目录。→ "从 GitHub 导入 Skill" 功能缺失。

## 缺失（需要新增）

### M1. 会话级 Skill 导入完全不存在

没有任何"session_id"维度的 skill 导入/绑定机制：
- `skill_ingestions` 表无 `session_id` 列（`skill_ingestion_runs.py:47-49`）
- `instruction_modules` 表无 `session_id`（`modules.py:20`）
- `project_modules` 表仅有 `project_id` 维度（`modules.py:21`）
- 前端没有任何"当前会话加载 skill"的 UI

当前所有 Skill 导入都是**永久**的：进入 `instruction_modules` 不可变表，绑定到 project 或 agent manifest。没有"新会话不继承"的隔离机制，因为根本没有会话维度的 skill 绑定。

### M2. GitHub / URL 来源的 Skill 直接导入

产品期望支持"从 GitHub 导入 Skill"。当前 `SkillIngestion.tsx` 入口仅支持：
- 本地 ZIP 上传（`file: UploadFile`）
- 管理员挂载目录（`FACTORY_SKILL_IMPORT_DIR`）
没有 GitHub URL 输入框或 `git clone` 逻辑。

### M3. 来源版本记录缺少 URL/commit 信息

`external_source` 记录了包 SHA256 和路径 SHA256（`skill_ingestion_runs.py:125-127`），但没有 `source_url`、`git_commit`、`git_repo` 字段。ZIP 上传后无法追溯到原始 GitHub repo 或版本。设计文档 §3 工具路径要求"接入声明与版本"。

### M4. 会话中断恢复的 Skill 持久化

产品期望"同一会话中断后恢复要保留"。当前 `agent_conversations` 表（`agents.py:322`）持久化了对话记录，但没有会话级 skill 绑定。对话恢复只恢复消息历史和 run 状态，不恢复 "本会话额外加载的 skill"。

## 会话作用域三问的明确答案

### Q1. 导入的 Skill 到底存到哪？

**存到 SQLite 永久表**。两条路径：
1. 适配路径：ZIP → `skill_ingestions` 表（BLOB + JSON）→ 人签后 → `skill_assets` 表（不可变 BLOB）+ `instruction_modules` 表（不可变 JSON）+ agent `manifest` 表
2. 直接附件路径：单 skill ZIP → `skill_assets` 表（不可变 BLOB）

没有内存存储、没有临时存储、没有 session-keyed 存储。一切都是磁盘上的 SQLite 永久行。

### Q2. "新会话不继承"是代码强制的还是碰巧不继承？

**概念不适用**。当前没有会话维度的 skill 绑定，所以不存在"继承"或"不继承"的问题。所有 skill 绑定在 agent manifest 或 project_modules 维度，这些维度**所有**会话都能看到——恰好是产品期望的反面。

换言之：当前行为是 **所有会话都继承所有已签署的 skill**，因为 manifest 和 project_modules 是全局的。要实现"新会话不继承"，需要新增 session-scoped 绑定表并从编排层区分。

### Q3. "恢复本会话保留"有没有对应的持久化？

**没有**。`agent_conversations` 表持久化了对话消息，`runs` 表持久化了运行状态和 `module_snapshot`（冻结在 run 上的模块快照）。但"本会话额外加载了哪些 skill"没有任何持久化载体。

`run.module_snapshot`（`modules.py:99-108`）是**运行级**冻结，不是会话级绑定。它记录的是 run 创建时项目 `project_modules` 的快照，用于保证运行期间模块版本不变。会话本身没有独立的 skill 集合概念。

## 不确定 / 需要主会话裁决

1. **"沉淀能力"（v3 Capability）归类**：它既不是纯方法也不是独立工具，是运行中提炼的"可重用工作模板"，主操作是 invoke（选项目→描述目标→开始工作）。产品概念中它更接近 Skill（方法），还是更接近工具？当前 UI 给它的标签是"沉淀能力"，动作是"开始工作"。
2. **会话级 Skill 的实现路径**：新增 `session_modules(session_id, module_id, version)` 表 + 在编排层合并读取？还是在现有 `agent_conversations` 表的 JSON 中增加 `loaded_skills` 字段？前者更规范，后者更简单。
3. **GitHub 导入的产品优先级**：设计文档提到但未给出 API 细节。是否需要在本轮实现，还是作为后续 TODO？
