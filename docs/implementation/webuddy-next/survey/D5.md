# D5 干预和恢复有效 — 现状调查（只读，基线 6fe1883）

## 自动接续触发条件（精确代码位置 + 它排除/不排除哪些终止原因）

自动接续有两个触发点：

1. **`service.py:268`** — `_job()` 的 `finally` 块。在 `active_jobs.pop(rid)` 之后检查：
   ```
   if self.store.get(rid)['status'] == 'needs_human' and _collect_pending_followups(self, rid):
       _auto_resume_with_followups(self, rid)
   ```
   **仅当 status == 'needs_human' 时触发**。cancel 设 status='cancelled'，不会命中。

2. **`recovery.py:167-170`** — 服务重启恢复收尾。在 `_ensure_scheduler()` 之后扫描所有 runs：
   ```
   if run['status'] == 'needs_human' and _collect_pending_followups(self, run['id']):
       _auto_resume_with_followups(self, run['id'])
   ```
   同样 **仅 needs_human**。cancelled/discarded/failed 全部排除。

3. **`run_lifecycle.py:97-100`** — `_auto_resume_with_followups()` 自身的入口守卫：
   ```
   if run['status'] != 'needs_human':
       return False
   ```
   即便被直接调用，也会对非 needs_human 状态返回 False。

**排除的终止原因**：cancelled, discarded, failed, inspection_failed, ready_for_review, published — 所有非 needs_human 的终态。
**不排除的**：仅 needs_human（即崩溃/超时/预算耗尽导致的执行中断）。

### 有幂等保护的操作

1. **GitHub 发布**（`github_publication.py:119, 94-173`）：

2. **远程部署 SSH 写操作**（`remote_targets.py:184-197`）：
   - `remote_invocations` 表以 `(run_id, target_id, verb)` 为主键。
   - 写操作前先 `INSERT OR IGNORE`；已有记录直接返回 cached 结果（`:192-197`）。
   - 注释 `:187`："动作已登记但未收到完成回执；请人工核对，不自动重放"。
   - 注释 `:208`："Never resume the external write"。

3. **Run 创建**（`run_routes.py:106-119`）：`delivery_id` 去重，同指纹返回已有 run。

4. **Followup 提交**（`run_routes.py:180-186`）：`idempotency_key` + `fingerprint` 去重。

5. **项目导入**（`project_import.py:42, 146-186`）：`(actor_id, request_key)` + fingerprint 幂等。

### 无幂等保护的操作

- **Agent 编码 worker 内部的 git push/文件写入**：worker 通过 Claude Code SDK 执行，平台不拦截重复 git push。但恢复时通过 `base_sha` 校验（`continue_run` 的 `baseline_sha(project) != artifacts['base_sha']` 检查，`run_lifecycle.py:310`），如果基线变化会 Conflict 而非静默重跑。
- **恢复执行时的编码调用**：`_continuous_resume_stage()` (`recovery.py:40-61`) 选择不需要重新编码的安全阶段（finalization/budget_finalization/verification），避免重放编码。但如果没有找到安全阶段，会从头重跑编码。

## 期望4 主动暂停/取消不自动重启：现状（这是重点）

**已实现，三重保护。**

### cancel 的状态转换

`cancel()` (`run_lifecycle.py:403-414`) 将 status 设为 `'cancelled'`：
```python
return self.store.update(rid, {'status': 'cancelled'},
    expected=('requirement_analysis', 'awaiting_spec_confirmation', 'received',
              'planning', 'queued', 'running', 'verifying', 'awaiting_approval',
              'needs_clarification', 'needs_human', 'ready_for_review'),
    event=('run.cancelled', {'message': '用户取消执行，保留日志和工作区', 'actor': actor}))
```

### 三层防止被自动拉起

1. **`_job` finally 块**（`service.py:268`）：`self.store.get(rid)['status'] == 'needs_human'` — cancelled 不命中。
2. **`_auto_resume_with_followups`**（`run_lifecycle.py:99`）：`run['status'] != 'needs_human'` → return False。
3. **recovery.py 重启恢复**（`recovery.py:92`）：`run['status'] not in ACTIVE` → `ACTIVE` 不含 cancelled → skip。recovery 末尾的 followup 扫描（`:168`）也只看 `needs_human`。

### cancel 期间的竞态保护

- `cancel()` 先设置 `cancels[rid]` 事件（`run_lifecycle.py:406`），使执行中的 worker 收到取消信号。
- `_RunCancellation` (`run_lifecycle.py:166-190`) 提供原子 Git 归档闸门 (`try_cancel()`)：如果 worker 正在做原子提交，cancel 被拒绝，用户收到 Conflict 提示。
- cancel 成功后 status='cancelled'，`_fail()` (`run_lifecycle.py:459`) 发现 status=='cancelled' 时直接 return，不会改回 needs_human。

### 取消后 followup 的处理

- T03/T08 回执明确："取消不清除未消费 pending（事件不可变）"、"取消状态保留 pending 原状，不自动恢复已取消任务"。
- 测试 `test_cancel_does_not_auto_resume`（T08 回执第 5 条）直接验证此场景。

### discard 的保护

`discard()` (`run_lifecycle.py:417-431`) 设 status='discarded'，同样不在 ACTIVE 和 needs_human 中，三层保护同时生效。

### 暂停（pause）

系统中无独立的 "pause" 操作。用户的 "暂停" 语义通过 cancel 实现（前端 `RunActions.tsx:22` 显示"取消运行"按钮）。budget 耗尽和 needs_human 是系统暂停，只有这类系统暂停允许自动接续。

## 不确定 / 需要主会话裁决

1. **是否需要独立 pause 操作**：当前 cancel 是终态，没有"暂停后原地恢复"。如果产品需要这一语义（暂停时保留 worktree 和执行上下文，恢复时继续而非重新规划），需要新增 `paused` 状态。但这超出"干预和恢复有效"的范畴，进入产品设计领域。
2. **Worker 内部操作的重复执行风险**：当 `_continuous_resume_stage()` 返回 None（无安全阶段可选）时，恢复会重跑编码。如果上一轮已完成部分文件写入但未 checkpoint，可能产生重复写入。当前通过 Git 分支隔离 + base_sha 校验 + checkpoint 机制缓解，但非严格幂等。是否需要更强保护需主会话判断。
