## 部分实现 / 需要修复

### P1. 工具产物可独立运行但**没有独立 CLI 包装**
- 当前工具入口是 `python3 -I tool/main.py`，请求通过 stdin JSON 传入，要求调用者自行准备 `input/`、`output/` 目录结构。
- **缺少**：argparse 或 typer 命令行包装（接受文件路径参数而非 stdin JSON）、`setup.py`/`pyproject.toml`、pip 可安装入口。
- **缺少**：用户可读的"平台外运行说明"，README 只描述功能不描述运行方法。
- 结论：技术上可以独立运行（本次实测已证明），但用户体验上需要了解契约协议才能使用。
- 文件：`factory/control/builtin_packs/tools/csv-quote-xml/README.md`（无运行说明）；`factory/control/builtin_packs/tools/mfd-xml/README.md`（同样）。

### P2. 工具自身不带版本标识
- `webuddy-pack.json` 没有 `version` 字段（版本号由平台发布时 `pack_versions` 表自增分配）。
- 工具程序文件内也没有 `__version__`。
- 下载的产物只带 sha256 和 validation_status，不带工具版本号（仅 CapabilityPanel 显示 `v{task.snapshot.version}`）。
- 如果用户把工具拷贝到平台外使用，无法从文件本身确定版本。
- 文件：`factory/control/builtin_packs/tools/csv-quote-xml/webuddy-pack.json`（无 version 字段）。

### P3. 下载产物的 sha256 核对仅在服务端执行，客户端无自动核对
- 服务端 `run_tool()` 在执行后计算 sha256 并存入 `pack_artifacts`（`pack_runtime.py:245`）。
- 下载端点 `pack_routes.py:248` 返回 `X-Validation-Status` 头和原始内容。
- **但**客户端没有在下载后重新计算 sha256 并与服务端值比对——`CapabilityPanel.tsx` 的下载是纯 `<a href=...>` 链接，浏览器原生下载。
- 如果传输过程中数据损坏或被篡改，用户不会收到警告。
- T04 回执的 sha256 比对是测试脚本手动做的，不是平台自动行为。

### P4. builtin pack 下载的 ZIP 是**职能体模板包（agent-pack）**而非工具执行包
- `agent_packs.py:38 pack_zip()` 生成的 ZIP 包含 `agent.json`（配置）、`SKILL.md`（指令）、`README.md`、`evaluations.json`、`fixtures/`。
- 这不是"可独立运行的 CLI"——它是给平台导入用的职能体模板。
- **没有**直接下载"工具执行包"（只含 tool/ + webuddy-pack.json）的端点。
- 文件：`factory/control/agent_packs.py:38-76`；`factory/control/agent_routes.py:114-121`。

## 缺失（需要新增）

### M1. 独立 CLI 入口（harness）
- 用户期望的"可独立运行的 CLI"不存在。需要一个最小 harness 脚本：接受命令行参数（输入文件路径）、自动创建临时目录结构、调用 tool/main.py、将产物复制到指定输出路径。
- 复杂度低：约 30-50 行 Python。

### M2. 工具执行包下载端点
- 当前只有 `/api/v4/builtin-packs/{slug}/download`（agent 模板 ZIP）和 `/api/v4/capability-packs/artifacts/{id}/download`（单个产物文件）。
- 缺少：按 pack_id + version_id 下载工具程序本体（tool/ 目录 + webuddy-pack.json + README）的端点。

### M3. 客户端 sha256 下载核对
- 下载产物后在浏览器端（或提供 CLI 命令）计算 sha256 并与服务端记录比对。
- 需要在 UI 上展示比对结果（match/mismatch），或至少展示 sha256 值供用户手动核对。

### M4. 版本标识嵌入工具产物
- 发布时将版本号写入 webuddy-pack.json（或生成一个 VERSION 文件），使平台外用户可以识别版本。

**工具层（mfd-xml）：诚实标注，无越界声称。**

以下 7 个位置均一致维持"局部提取"口径，没有任何一处将其描述为完整/无损转换：

| 位置 | 文件:行 | 原文关键词 |

| manifest purpose | `tools/mfd-xml/webuddy-pack.json:4` | `"这是局部记录提取，不是整文件无损转换"` |
| support_matrix unsupported | `tools/mfd-xml/webuddy-pack.json:39` | `"本包不做也不声称"` |
| main.py docstring | `tools/mfd-xml/tool/main.py:5` | `"不是整文件无损转换"` |

| xml_writer.py 注释 | `tools/mfd-xml/tool/xml_writer.py:11` | `"不是无损转换"` |

| README.md | `tools/mfd-xml/README.md:16` | `"不做整文件分帧，不声称无损转换"` |

**但 agent pack 层（mfd-xml-conversion）存在口径不一致：**

- `packs/mfd-xml-conversion/pack.json:4` purpose 写的是 `"把江苏未来计价软件的 MFD 项目文件无损转换为江苏标准 XML"`。
- 这个 purpose 会流入 `agents` 表的 purpose 字段（`agent_packs.py:105`），并在前端 AgentsPage.tsx 中以"业务用途"展示给用户（`AgentsPage.tsx:183` `<p>{agent.purpose}</p>`）。
- **效果**：用户在职能体目录页看到的用途描述是"无损转换"，点进去调用工具时看到的 tool_contract.purpose 是"局部提取"。两层口径矛盾。
- **注意**：pack 的 `validation_status: "template-unbenchmarked"` 说明这是未经基准验证的模板，purpose 描述的是**目标**而非**现状**。但 UI 上没有区分"目标"与"已实现"，用户可能误解为已具备能力。

## 不确定 / 需要主会话裁决

1. **pack.json purpose 的"无损转换"措辞是否需要改为"目标：无损转换"或"开发中"**？当前 UI 不区分目标与已实现。这是口径问题而非功能问题——修复代价极低（改一行字符串），但需要产品决策。
2. **独立 CLI 包装的优先级**：当前工具技术上可独立运行但用户体验差。是 P0（必须有 CLI）还是 P2（文档补说明即可）？
3. **客户端 sha256 核对的实现方式**：浏览器下载（`<a href>`）无法拦截内容做 hash。选项：(a) 改为 JS Fetch + Blob + 前端 hash；(b) 下载页面显示 sha256 供手动比对；(c) 提供 CLI 下载命令自动核对。
4. **工具执行包下载端点**是否需要单独做，还是在 agent pack ZIP 中加入 tool/ 子目录即可？
