# D6 完整软件交付路径 — 现状调查（只读，基线 6fe1883）

## 链路分段现状表

### 1. 需求 → 编码 → 测试：已实现

- 需求提交：`factory/control/run_routes.py:30-118` — 用户通过 POST /api/v2/runs 提交需求，支持 operation 类型（general/bugfix/startup/release/dependencies）。
- 编码执行：`factory/control/execution.py` + `factory/control/run_execution.py` — ThreadPoolExecutor 调度真实 SDK worker 执行编码。
- 测试验证：`factory/control/verification.py` — 独立验收阶段，verdict pass/fail/invalid_response。
- 真实执行点：`factory/control/service.py:52-57` — Service.__init__ 接收 runner（SDKRunner）和 publisher（GitHubDelivery），均为真实实现。

### 2. GitHub 绑定与发布：已实现

- **仓库绑定**：`factory/control/github_publication.py:58-92` — GitHubPublication.bind() 将项目关联到真实 GitHub 仓库（全称 owner/repo），写入 project_settings_audit 审计表，发出 github.repository_bound 事件。
- **发布**：`factory/control/github_publication.py:95-164` — GitHubPublication.publish() 支持三种模式（bound/existing/create），创建持久化收据（github_publication_requests 表），crash-safe。
- **真实 git push**：`factory/control/github.py:148-207` — GitHubDelivery.publish() 通过 subprocess 调用真实 git push，使用 FACTORY_GITHUB_TOKEN 认证，推送到 github.com。
- **产物类型**：首次推送到空仓库 → publication_type='initial'（直接推送到 base branch）；已有历史 → publication_type='pull_request'（创建 PR）。
- **前端 UI**：`frontend/src/workbench/GithubDelivery.tsx` — 管理员选择已有仓库/创建私有仓库/使用当前绑定仓库，点击上传。
- **前端测试**：`frontend/src/workbench/GithubDelivery.test.tsx` — 12 条测试覆盖标签、请求体、权限分离、链接安全。
- **API 路由**：`factory/control/run_routes.py:229-256` — GET /api/v3/runs/{rid}/github-options, POST /api/v3/runs/{rid}/github-publish。
- **凭据初始化**：`factory/control/app.py:92-93` — 读取环境变量 FACTORY_GITHUB_TOKEN，有值则创建 GitHubDelivery 实例。
- **无 mock/stub 兜底**：publisher=None 时所有发布操作抛出 Conflict 异常，不会静默跳过。

### 3. 部署目标（公司固定测试地址概念）：已实现（概念存在，值为配置缺口）

- **部署目标注册**：`factory/control/deploy_targets.py:81-157` — TargetStore 管理 deploy_targets 表，每个目标包含 name/host/port/user/host_fingerprint/commands（五个预注册动作：health_check/service_status/fetch_log/deploy/rollback）。
- **ED25519 密钥对**：`factory/control/deploy_targets.py:111-127` — 创建目标时自动生成密钥对，私钥存放在 FACTORY_DEPLOY_KEY_DIR 独立目录，公钥展示给管理员复制到目标服务器。
- **项目绑定**：`factory/control/deploy_targets.py:160-178` — 每个项目最多绑定 8 个目标，通过 project_deploy_targets 表关联。
- **真实 SSH 执行**：`factory/control/remote_targets.py:67-99` — RemoteTargets._ssh() 调用真实 ssh 命令，严格主机指纹验证（StrictHostKeyChecking=yes）、禁用代理转发和密码认证。
- **部署执行**：`factory/control/remote_targets.py:143-198` — execute() 方法执行注册的 deploy 命令，仅当 operation='release' 且 execute_deploy=True 且验收通过时允许写操作。deploy 执行有 crash-safe 的 remote_invocations 收据表。
- **连接检查**：`factory/control/remote_targets.py:199-210` — test() 方法只运行 `true` 命令验证 SSH 连通性和主机指纹。
- **health_check 支持 URL**：`factory/control/remote_targets.py:116` — 如果 health_check 命令以 http:// 或 https:// 开头，自动包装为 curl 命令。**这是最接近"固定测试地址"的概念——管理员可以在 health_check 命令中配置一个 URL，但这是个命令字段，不是独立的"固定测试地址"字段。**
- **前端 UI**：`frontend/src/workbench/ServerTargets.tsx` — "公司测试环境"配置区，aria-label="公司测试环境"，section id="company-environment"。支持注册/编辑/删除目标、复制公钥、检查连接。
- **前端测试**：`frontend/src/workbench/ServerTargets.test.tsx` — 133 行，覆盖空状态、加载、检查结果、连接测试。
- **API 路由**：`factory/control/remote_routes.py` — 完整 CRUD + test + bind + execute 路由，全部 admin 权限。

### 4. "固定测试地址"供用户实际操作：部分实现

- **没有独立的 "固定测试地址" 或 "staging URL" 字段**：在整个 factory/ 和 frontend/src/ 中搜索 deployed_url/test_url/fixed_url/staging_url/preview_url/base_url/访问地址/测试地址/固定地址，均无结果。
- **最接近的机制**：deploy_targets 的 health_check 命令可以配置为 HTTP URL（`remote_targets.py:116`），deploy 命令可以是部署脚本路径。这些命令由 SSH 在目标服务器上执行，用户通过远程结果（remote_results）看到退出码和输出摘要。
- **用户无法在 UI 上直接点击打开测试地址**：Deliverables.tsx 的 DeliverableDeliverySection 对 service 类型只显示"已部署"/"待部署"文案，没有可点击的 URL 链接。
- **结论**：部署目标的概念已完整（host/port/user/commands 五动作），但"用户在固定地址上做实际核心操作"这一步缺少一个可展示给用户的 URL 字段。这是**概念部分缺失/字段缺失**——deploy_targets 表和 UI 都没有 url/service_url 字段。

### 5. 同一地址更新（二次修改 → 重新部署）：已实现

- **同一项目多次运行**：项目通过 repository 字段绑定到同一 GitHub 仓库（`github_publication.py:71-91`），后续运行的发布都推送到同一仓库。
- **部署目标通过项目绑定**：project_deploy_targets 表按 project_id 绑定，所有该项目的 release 运行都向同一组目标执行 deploy 命令（`remote_targets.py:217-248`）。
- **重新部署链路**：用户提交新的 release 运行 → 编码/测试 → 验收通过 → 管理员再次执行远程 deploy → 同一目标上的 deploy 脚本被再次调用。
- **基线同步**：`github_publication.py:166-193` — sync_initial_baseline() 在首次发布后 fast-forward 本地项目基线。

### 6. 版本可追溯：已实现

- **GitHub 提交 SHA**：每次发布记录 commit SHA（`github.py:161-162`），存入 run.artifacts。
- **PR URL 和编号**：`github.py:179-183` — publication_type='pull_request' 时记录 pr_url 和 pr_number。
- **工厂分支名**：`github.py:161` — 每次发布使用 factory/xxx 分支名，分支在 GitHub 上可追溯。
- **合并确认**：`run_lifecycle.py:434-453` — sync_merge() 通过 GitHub API 验证 PR 是否已合并，记录 merge_commit_sha 和 merged_at。
- **事件审计流**：`store.py:59-86` — events 表 append-only（有数据库触发器禁止 UPDATE/DELETE），记录 github.repository_bound / github.publish_started / github.published / github.merge_confirmed / github.publish_failed。
- **项目设置审计**：`store.py:71-86` — project_settings_audit 表同样 append-only，记录仓库绑定变更。
- **部署收据**：`remote_targets.py:183-191` — remote_invocations 表按 (run_id, target_id, verb) 去重，记录每次远程执行结果。
- **计划版本**：`frontend/src/workbench/PlanVersions.tsx` — 展示最近 100 个计划版本及其修订号、时间戳、任务范围。
- **成果归档**：`factory/control/deliverables.py:36-116` — snapshot() 将验收版本的所有文件打包为 ZIP，含 manifest.json（commit SHA、文件列表、SHA256 校验值）。

## 代码缺口（本轮可补）

1. **deploy_targets 缺少 service_url / test_url 字段**：用户期望在 UI 上看到并点击一个"固定测试地址"来实际操作产品。当前 deploy_targets 只有 host/port/user/commands 五项，没有可展示的 URL 字段。health_check 命令虽然支持 HTTP URL，但它是个执行命令，不是给用户看的地址。需要在 TargetStore 增加一个可选的 service_url 字段，并在 ServerTargets.tsx、Deliverables.tsx、ProjectTargets 中展示为可点击链接。
   - 后端改动点：`factory/control/deploy_targets.py:84-106`（validate 增加 service_url 字段）
   - 前端改动点：`frontend/src/workbench/ServerTargets.tsx`（注册表单增加字段）、`frontend/src/workbench/Deliverables.tsx:79-97`（DeliverableDeliverySection 展示 URL 链接）

2. **Deliverables.tsx 中 service 类型只有文案，没有链接**：DeliverableDeliverySection 对 service 类型显示"已部署/待部署"（`Deliverables.tsx:93-96`），没有从 deploy_targets 拉取可点击的地址。即使补了 service_url 字段，前端也需要改这里来展示。

## 环境/业务配置缺口（需要用户或运维提供，本轮补不了）

1. **FACTORY_GITHUB_TOKEN 未配置**（codex-handoff.md 确认）：生产环境需要管理员配置此环境变量，否则 publisher=None，所有发布操作被拒绝。这是环境配置，不是代码问题。
2. **FACTORY_DEPLOY_KEY_DIR 未配置**：部署目标需要此目录存放 SSH 密钥。同为环境配置。
3. **部署目标未注册**（codex-handoff.md 末尾"固定测试地址未明确；生产部署目标登记为空"）：即使代码完整，也需要管理员在 UI 中注册真实的主机地址、SSH 用户、主机指纹、deploy/health_check 命令。
4. **部署脚本由目标服务器自行维护**（ServerTargets.tsx 文案："命令中不要填写凭据；脚本由目标服务器自行拉取产物，本平台不传输文件"）：平台只通过 SSH 触发预注册命令，不上传代码到目标服务器。目标服务器上的部署脚本需要运维编写和维护。
5. **固定测试地址的实际值**：即使补了 service_url 字段，URL 的值需要用户/运维提供（如 https://test.company.com）。

## 版本可追溯现状

完整。每次交付有以下可追溯记录：
- Git commit SHA（40 字符，存入 run.artifacts.commit）
- GitHub 仓库 URL（run.artifacts.repository_url）
- PR URL 和编号（run.artifacts.pr_url / pr_number，增量发布时）
- 工厂分支名（run.artifacts.branch，格式 factory/xxx）
- 发布类型（run.artifacts.publication_type: initial / pull_request）
- 合并证据（run.artifacts.merge_evidence，含 merge_commit_sha / merged_at）
- Append-only 事件流（events 表，有 DB 触发器禁止篡改）
- 项目设置审计流（project_settings_audit 表，同样 append-only）
- 远程执行收据（remote_invocations 表，按 run_id+target_id+verb 去重）
- 成果 ZIP + manifest.json（含每个文件的 SHA256）

## 不确定 / 需要主会话裁决

1. **"固定测试地址"是否等同于 deploy_targets 的扩展？** 当前 deploy_targets 是 SSH 目标，适合后端服务部署场景。如果用户的项目是纯前端/静态站（部署到 Vercel/Netlify/Pages 等），当前机制不适用。需要确认用户场景是否只覆盖 SSH 可达的服务器。
2. **deploy 命令的执行结果是否需要解析出 URL？** 比如 deploy 脚本输出一个 URL，系统是否应该捕获并展示？当前只保存退出码和 summary（前 12000 字符，已脱敏）。
3. **codex-handoff.md 中"V1-03 线上段：真实 GitHub bind→publish"已由 Codex 验收通过**（见 r2 交接"T08 auto-resume 首段无人观察成立"等记录），但"固定测试地址业务操作"仍标记为未验收。
