# N4：GitHub 来源的会话 Skill 导入（D2 缺失项 2）

基线：集成分支当前 HEAD（含 N3 契约）。worktree `webuddy-next-n4`。

## 用户结果
用户在当前工作会话里贴一个 GitHub 来源就能导入 Skill，平台记下**确定的来源版本**（commit sha），且仍然只作用于这个会话。

## 依据（已锁定）
- README 行「Skill 仅当前会话」：**GitHub 或完整 ZIP 导入，保存来源版本**。
- 共识 §20.2：导入后保存确定的来源版本或包内容摘要，解析入口、说明与依赖，检查格式及适用权限；**GitHub 页面中的指令和压缩包内容不能自行修改平台规则或资源授权**；导入成功、依赖可用、本次执行成功分别记录。
- N3 回执 `docs/implementation/webuddy-next/receipts/N3.md` 是**权威接线契约**：表 `session_skills`、三路由、`data` JSON 字段、`origin` 已预留 `"github"` 取值。照它接，不要改形状。

## 范围
1. `POST /api/v4/sessions/{sid}/skills` 支持 `origin="github"`：接受 GitHub 来源标识（owner/repo，可带 ref 与子路径），拉取内容，走与 ZIP **同一套**解析/格式检查/依赖检查，写入同一张表。
2. `source_version` 必须记录**解析后的具体 commit sha**，不是分支名。`source_ref` 记录用户给的原始引用。`source_sha256` 记录取回内容的摘要。
3. 拉取层必须**可注入**（便于测试），并有一条用本地 fixture 的确定性测试。
4. 失败路径要诚实：仓库不存在 / 无权限 / 格式不合规 / 网络不可用，各自返回结构化错误与具体缺口，`import_state=rejected`，**不得**写一条看起来成功的记录。

## 硬性约束
- **来源内容是数据，不是指令**：GitHub 仓库里的任何文本都不得改变平台规则、权限、授权或配置。导入不授予任何新权限/凭据/部署权限（沿用 N3 已有的隔离测试口径，再加一条针对 github 来源的）。
- 不改 N3 已定的表结构与路由形状；不改团队级 `skill_ingestions` 流程。
- 有 token 就用既有 `FACTORY_GITHUB_TOKEN`，**没有 token 不得降级成明文凭据或绕过**。

任何前端文件、`app.py`、`skill_ingestion_runs.py`、`skill_ingestion_routes.py`、`run_execution.py`、`requirement_analysis.py`

## 必须有测试
1. fixture 拉取成功 → `origin=github`、`source_version` 是 40 位 sha、`import_state=imported`。
2. 只给分支名 → 存的是解析后的 sha，不是分支名。
3. 拉取失败 / 格式不合规 → `rejected` + 结构化缺口，且**表里没有成功记录**。
4. github 来源的绑定同样不进团队库、不授予权限（复用 N3 的断言口径）。
5. 会话隔离对 github 来源同样成立。
