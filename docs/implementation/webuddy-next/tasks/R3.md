## Codex 的判定（事实，不要辩驳）
`agent_routes.py:707–735`：创建 pending 后，完成任务**只追加 completed 消息，不结束原 pending**；错误路径同样追加 failed 而不清 pending。
`AdminConfigChat.tsx` 以**任意 pending** 决定轮询与禁用/等待状态，且**只有 pending 全部结束才调用 `onConfigChanged`**。
后果："后台确实改了值" 和 "用户页面完成并刷新表单" 不是一回事——轮询永不停止，表单永不刷新。

## 修复范围（Codex 给定）
1. **按 job/message 关联更新生命周期**——完成时要结束的是那条 pending，不是另追加一条。
2. **pending 必须在派发前持久化**，避免快速完成后旧 conv 回写覆盖结果（这是真实的竞态，不是理论问题）。
3. **成功、失败、取消/中断都要有真实终态**。
4. **已有 pending 依据作业状态恢复，不盲目标成功**。
5. **保持消息事务性，防并发覆盖。**
6. **补一个前端行为验证**：完成 → 停止轮询 → 刷新同一表单。
7. **不要新增另一套作业框架**，沿用现有 maintenance job 机制。
