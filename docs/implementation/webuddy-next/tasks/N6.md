## 用户结果
用户在成果上能看到：这一版**实际加载了哪些 Skill**、**实际调用了哪些工具**、成果部署在哪个**固定测试地址**，并能直接**继续修改**。没有记录时明确显示「缺记录」，不编造。

## 依据（已锁定，不要重新设计）
- README 行「成果优先展示」：历史作品直接提供打开、下载、继续修改；显示对应版本实际加载/调用的能力，**缺记录不编造**。
- 共识 §22：**仅加载标为已加载，有实际调用证据才标已调用；缺少历史记录不靠名称或模型总结补造**。详细版本、执行器、验证及日志按需展开。
- 术语对齐 §1/§4：Skill 的动作是**加载**，工具的动作是**使用/调用**；两类不能套同一组字段；「加载了逆向 Skill」**不等于**「转换器已就绪」。
- 调查报告 `survey/D1.md`：后端 `tool.call` 事件已持久化在 events 表（真实记录，非硬编码），前端只有原始事件流/日志时间线，**没有聚合摘要 UI**；`delivery_type` 前端展示上一轮缺口**已不成立**，不要重做。
- 调查报告 `survey/D6.md` + N8 回执 `receipts/N8.md`：`service_url` 字段已就绪，出现在 `GET /api/v2/projects/{pid}/deploy-targets` 的 available 数组（member 也可见，且只暴露 id/name/revision/service_url）。

## 范围
1. **后端聚合**：给定 run，返回能力来源摘要
   - 已加载（loaded）：来自 `module_snapshot` + N3 的 `session_skill_snapshot`（两者来源要分得清：项目模块 vs 本会话导入）
   - 已调用（invoked）：来自 events 表里真实的 `tool.call` 记录
   - **两类分别返回，不合并成一个「能力」列表**
   - 无记录时返回明确的「无记录」标记，**不要返回空数组让前端猜**
2. **前端摘要面板**：在成果视图展示上面两类，动词分别是「已加载」和「已调用」；无记录显示「缺记录」文案而不是留空或写「无」。
3. **继续修改入口**：成果视图（delivery view）加「继续修改」操作，关联正确的项目与版本，复用既有后续 run 发起接口，**不新建一套**。
4. **固定测试地址**：service 类型成果展示 `service_url` 可点击链接；未登记时显示「未登记固定地址，请管理员补齐」。

## 硬性约束
- **禁止编造**：面板里任何一条都必须能追到真实记录。不得用模块名称推断「调用过」，不得用模型总结补造。
- 加载 ≠ 调用：只加载没调用的，只能出现在「已加载」。
- 沿用统一 AppShell 与既有米白墨绿视觉，不新造导航、不新增顶层路由。
