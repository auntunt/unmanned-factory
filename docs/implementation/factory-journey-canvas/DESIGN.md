# 设计决定：维护监控入口与工程关系画布（2026-09-23）

基线：`5680fe4`（待验收候选，未上线）。本页先根据现有代码纠正实施单里的假设，再给出决定。

## 现状核对（证据）
- **监控行没有下钻入口**（已证实）：`MonitorPage.ProjectRowView` 只渲染文本，没有任何链接。子系统外框 `MaintenanceShell` 已经有“维护代码库”标签；缺的是从行进入仓库详情。
- **仓库详情缺检查时说明不足**：`ReposPage` 在没有建议检查时不显示任何内容。真实可行的下一步是主工作台的 `/projects/{id}#project-checks`（`ChecksEditor`，`PUT /api/v2/projects/{id}`，仅管理员）。嵌入模式下不能跳出嵌入前缀。
- **画布已经存在，但只有骨架**：`RelationCanvas.tsx` 已有平移、缩放、适应视图和侧栏。数据来自 `MaintenanceSubsystem.graph()`，节点是 代码库→需求→任务→补丁/目标/阻塞，服务端按 `_scope(actor)` 过滤，与 `governance.require_project` 同一套授权。缺的是：版本、责任人、方案和检查这两个实际阶段、证据与详情链接、项目筛选、定位选中、键盘和列表路径、返回时保持视图。
- **事实来源**：任务 `base_sha`（登记时钉住的基线）；执行 `run.source.actor`（发起人）；`engineering_overview.current_evidence(run)` 给出 plan / checks(`none|passed|failed|recorded|unverified`) / delivery；`artifacts.checks[]` 是 `{name, argv, exit}`；补丁由 `artifacts.commit` 判定；需求 `source.kind/name`；仓库 probe 的 `base_sha/branch/needs`。**项目没有负责人字段**，任务的当前经办人也没有字段；可以证实的只有“谁发起了执行”，以及既有规则“发起人或管理员可以处理”。

## 决定
1. **不新增写模型，也不迁表**：在现有 `graph()` 投影里补充只读事实（`facts[]`、`links[]`、`tone`），节点保持向后兼容（原字段不变）。授权沿用 `_scope`，不在前端过滤。
2. **节点链 = 实际阶段**：代码库 →(has) 需求 →(creates) 任务 →(plans) 方案 →(verified_by) 检查 →(produces) 补丁 / (targets) 目标。阻塞挂在它真正卡住的阶段上：待批准挂在方案上，待回答和受阻挂在任务上。没有记录的阶段显示“尚无记录”，不推断为完成。补丁节点注明“已生成 ≠ 已验收 ≠ 已上线”。
3. **人和执行器分开**：负责人一律显示“未记录（系统没有该字段）”；显示“执行发起人 X”，待处理时显示“可处理：发起人 X 或管理员”；执行器只写已记录的 provider，没有就写“未记录”。不出现拟人化的多 Agent 角色。
4. **交互**：沿用现有画布组件并增强：项目筛选（走服务端 `project_id`）、“定位选中”、节点按类型着色（4 种语义：正常 / 待处理 / 受阻 / 无记录）、连线标注含义、长标题截断并可在侧栏看全文；侧栏给出来源 ID 和真实入口（仓库详情、任务现场）。视图、项目和选中节点写入 URL 查询参数，从任务现场返回时原样恢复。
5. **可达性**：画布旁提供“列表”视图（同一份投影，按层级缩进，全部是可聚焦的链接或按钮）；窄屏默认显示列表。不依赖拖拽也能完成全部路径。
6. **第一批（独立提交）**：监控行的项目名、“查看待补充项 / 查看接入失败原因 / 查看项目”都链接到 `mp('/repos/'+encodeURIComponent(id))`；状态徽标保持纯文本。仓库详情在没有建议检查时如实说明，并给出可执行的下一步（管理员且非嵌入时链接到项目检查设置；其他情况说明需要管理员配置），不采纳、不执行客户检查。

## 不做
不建 WorkItem 写模型；不伪造负责人或完成状态；不接入 Grok 或新的代理框架；不改授权和凭据逻辑；不写 webuddy-desktop。
