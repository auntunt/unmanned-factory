## 3. 三个场景的页面入口、使用步骤、证据位置

前置：管理员在 **设置 → 业务插件**（`/settings/plugins`）里启用对应插件。
未启用时页面不提供新建入口，服务端也会拒绝——这是出厂默认，不是故障。

### 信创化改造 · `/modernization`

登记项目与约束 → 分析 → 创建改造切片 → 澄清/批准 → 修改 → 检查 → 补丁与回执

1. `/projects` 登记项目（仓库、基础分支、验收检查）。
2. `/modernization` 选项目，在「改造维度与目标」登记目标（默认 **候选**，
   不是已批准），人工「确认」某一维才变成已确认约束。
3. 「依赖处置计划」看各维度状态与代码定位（定位来源与新鲜度随结果返回；
   没建索引就明说没建，不编造定位）。
4. 「新建切片」：维度、范围路径、40 位基线 SHA、期望行为、交付目标、已知缺口。
5. 详情页：模型提问 → 填写回答 → 提交 → 重新规划 → 「批准计划」。
6. 执行后看检查结果与未验证项，「导出回执」「下载补丁」。

**证据**：真实模型端到端跑通一条（规划→批准→改码→项目检查 exit=0→提交→交付），
见 `EVIDENCE-real-model.md` 第一节；补丁与校验值在 `evidence/`。
澄清交互用脚本规划器在浏览器走通，见 `evidence/clarification-walkthrough.md`。

### 自动化运维 · `/maintenance`

输入问题 → 定位 → 计划 → 澄清/批准 → 修复 → 检查 → 补丁与回执

1. `/maintenance` 选项目，「新建任务」填 Issue 原文、基线 SHA、期望行为、交付目标。
   方法版本由服务端按已安装方法包给出，不接受手工填写。
2. 详情页：进度、阻塞原因、模型提问时的回答入口、「批准计划」。
3. 「补充」可在人工节点追加信息；交付后「导出回执」「下载补丁」。
4. 交付出回执时把这次改到的路径与 commit 写回项目记忆（`candidate`）。

**证据**：`b854a41` 冻结里程碑里用脚本执行器走通过完整网页闭环；
本候选新增的澄清交互有定向路由测试与页面测试。
**本候选没有用真实模型跑过维护场景**——这一条不要写成已验证。

### 三方接口适配 · `/adaptation`

登记接口与契约 → 明确映射 → 澄清/批准 → 实现 → 契约检查 → 结果与回执

1. `/adaptation` 选项目，「新建任务」填来源接口（名称/版本/base_url/鉴权/环境）、
   目标 Adapter、字段规格、HTTP 操作、**字段映射矩阵**、业务报文。
   无法映射的字段必须写明影响，不允许静默丢弃。方法版本同样由服务端给出。
2. 详情页：映射矩阵（待确认字段单独高亮）、模型提问的回答入口、「批准计划」。
3. 执行后看**业务调用结果**：技术成功 / 业务受理 / 业务完成三个状态分开，
   mock 单独打标；「导出回执」「下载补丁」。

**证据**：真实模型端到端跑通一条，含一轮澄清问答，见 `EVIDENCE-real-model.md`
第二节；补丁 SHA-256 与回执 `diff_hash` 逐字符一致。
**第三方是本机模拟端**（检查进程内起的 `127.0.0.1` HTTPServer），
`environment=mock` 原样进回执。**这不是客户业务完成，也不是客户接口验收。**

### 证据分级一览

| 场景 | 真实模型验证 | 脚本规划器验证 | 依赖客户材料 |
|---|---|---|---|
| 信创化改造 | 一条 database 维度切片（合成仓库） | 澄清交互浏览器演练 | 真实达梦实例、其余五个维度、客户仓库 |
| 自动化运维 | **无** | 完整网页闭环（`b854a41` 里程碑）+ 澄清交互 | 客户 Issue 原文与分支 |
| 三方接口适配 | 一条报文含澄清轮（合成契约 + 本机模拟端） | 澄清交互浏览器演练 | 真实接口规范、鉴权、沙箱、业务验收人 |

## 4. 已知限制、服务器验收步骤、回退注意事项

### 已知限制

- 三个场景的真实业务效果、客户验收、生产部署**都没有验证**。
- 适配面没有 `resume` 与 `follow-up` 入口；停在非提问类人工节点时只能取消。
- 信创只验证了 `database` 一个维度；其余五个维度的命中词表没有在真实项目上验证。
- 代码图的语言能力只在最小样例上验证：Java/Python/C#/Go 的检索与跨文件关系可用，
  C/C++ 仅最小样例，**Rust 的关系层实测未解析、本期后置**。
  C#/.NET 的「能构建改造」在本机无法验证（没有 dotnet），.NET Framework 还需要 Windows。
- 索引只覆盖**已提交的 commit**；工作树里未提交的改动不在索引里（结果里带
  `indexed_commit` 与 `source_dirty`，不要把图当实时工作副本）。
- `refine_memory_for_plan` 只是给复核看的记录，**执行器没有消费**它。
- 截图没有存成 PNG 文件（工具只把图返回到会话）。**下次页面验收时需要补采**：
  三个列表页、三个详情页的问答面板、回答后的「批准计划」入口、交付后的回执与
  补丁下载——共约 8 张；同时在清理临时数据**之前**归档机器可读的事件与回执。

### 服务器验收步骤（建议顺序）

1. 部署候选，确认服务起得来、既有维护面不受影响。
2. 管理员进 `/settings/plugins`，把 `legacy-modernization` 与 `api-adaptation`
   从「已停用」改为「已启用」（出厂默认是关的）。
3. 按第 3 节的步骤各走一条合成切片。真实模型需要该 provider 自己的凭据与预算。
4. 归档事件、回执、补丁与 PNG。

### 回退注意事项

**切换代码版本不等于完整回滚。** 本候选惰性新建了 8 张表并会写入业务行
（插件可用性与审计、信创切片与回执、适配任务与回执）。回退代码之后：

- 这些表和里面的数据**仍然留在库里**，旧代码不会读也不会清理它们；
- `plugin_availability_audit` 有「禁止改删」触发器，**不能**用 DELETE 清理，
  要清只能重建库或整表重建；
- 已经交付的切片/任务的回执与补丁只能通过新代码的导出接口取；回退后取不到；
- `FACTORY_CODE_INDEX_HOME` 下的索引工作副本是 `git worktree`，回退代码不会
  清理；如需清理要用 `git worktree remove`，直接 `rm -rf` 会在主仓库留下悬空登记。

因此回滚计划要**先决定这些业务数据怎么处理**，再谈切代码版本。
