# 主动验收与逐项证据

本轮沿用持续开发、六环看板、DAG 和挂载清单，补齐执行与验收之间的能力差异。

## 已实现

- 控制层从交付提交读取 Git 原始对象，批量创建临时验收副本；忽略目录里的未提交文件、凭据和依赖不会随之复制。Git 的 export-ignore/export-subst 不会改变验收内容。
- Claude 验收仍关闭原生写入/编辑工具，但开放隔离终端和项目浏览器。测试可以生成临时探针、依赖与构建输出；原有源码、测试、配置一旦被改变或删除，整个验收无效。验收副本永不合并回交付物。
- Codex 验收在临时副本使用 workspace-write 沙箱；普通只读规划仍是 read-only。DSH 的只读能力限制保持原样。
- 每次新验收创建干净会话；同次快照内的连接故障可以接续。原开发会话与代码现场保留。
- 每条任务与职能体验收条件有稳定编号、结论、证据。平台计算覆盖数量，缺项、重复编号、空证据、未验证条件不能获得整体通过。没有细分条件的旧任务用原始需求作为一个条件。
- 仅报告漏项时，先在剩余验收时限和预算内补证据一次，不让开发重新执行。仍不完整则明确记录 incomplete_coverage。
- 真实业务失败回到开发现场修复，指令包含复现、根因、同一规则的影响面、原问题回归与检查器误报核对。没有新增证据时不做无边界全库审计。
- 独立浏览器观察进入日志，未解决错误会拒绝整体通过。PNG 截图保存至控制数据库旁的 verification-evidence/run-id，临时副本清理后仍保留；拒绝现场外文件和超过 8 MB 的截图。
- 六环现有验证页面展示逐项通过、失败、未验证与证据，无新增审批步骤。

## 适用边界

逐项覆盖可以阻止漏项和空证据，不等于平台能机械证明每段模型解释正确。命令实际记录、具体输入输出与浏览器观察仍需结合业务契约判断。

批量任务沿用现有 DAG、依赖与冲突调度。这轮统计的是约定的验收条件，不把目录数量伪装成“合格垂直智能体数量”。通用的业务成果注册表、自动跨项目参考包提取尚未实现；原有版本化 Skill 和资料挂载继续可用。

验收快照限制为 50,000 个文件、300 MB；未展开的 Git 子模块和指向现场外的符号链接明确拒绝。副本不会携带 node_modules 或虚拟环境，首次验证可能需要安装依赖。共享引擎是否应该抽取由当前任务负责人结合实际重复点判断，平台不强制所有项目模板化。

验证过程中新增文件允许用于探针和构建，原有文件的最终内容、模式及链接必须保持一致。该检查不是“任意测试代码不可作弊”的形式化证明；验证来源与复现样例依然重要。
