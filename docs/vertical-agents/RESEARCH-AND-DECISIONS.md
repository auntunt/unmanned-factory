## 官方参考

### Agent Skills 格式与渐进加载

[Agent Skills specification](https://agentskills.io/specification) 规定入口 SKILL.md 和可选 scripts/references/assets；技能可按元数据、正文、资源逐层加载。其 allowed-tools 字段仍为实验性，宿主支持不一。因此本设计保留原多文件包、具体内容哈希与按需加载，但工具授权由工厂独立执行。格式规范不能替代脚本安全检查或领域评测。

### 固定工作流和自主任务分解

[Anthropic — Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 区分固定路径的 workflow 与模型动态决定流程的 agent，并强调按实际需要增加复杂度。本文较早，页面亦提示工具生态已有变化；本设计只采用其工作流/动态分解的概念，不沿用过时 SDK 示例。对本项目采用标准工程阶段、受控专业分支和显式工作单元，而非一开始开放无限 Agent 自建流程。

### 上下文与长期状态

[Anthropic — Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 讨论按需检索、上下文管理及长期任务状态。由此结合现有快照机制，选择给职能传递必要证据与明确产物引用，并将项目事实、Skill 方法、数据集和运行状态分别持久化；不让所有职能复制整段对话。

### 连接器授权

[MCP Authorization — 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) 是特定协议版本的授权规范，不能直接等同工厂的工具权限。设计将 provider/connector credential reference 与 Agent 工具允许范围分开；若后续采用 MCP，仍需工厂的资源授权、撤销、审计和执行边界。首版不为导入 Skill 自动连接其提及的外部服务。

## 核心 ADR

### ADR-01：新建 Agent 对象，保留 Capability 兼容层

采用独立专业配置实体，引用 Skill 和既有能力来源。原因：未来需要多职能、多模型、工具环境、评测与发布生命周期，超出现有文本能力定义。代价：需要新 UI、编译器和版本模型；通过“从能力创建智能体”提供迁移路径，不重写历史。

### ADR-02：职能先于多进程 Agent

角色表示职责和验证边界，是否并行由依赖/文件范围/资源决定。原因：同一平台可服务很多专业配置，不意味着每个配置或每个角色都要常驻进程。复用现有池与持久队列，先实现少量受控流程。

### ADR-03：导入是素材管理，不等于启用

原始包不可变，规范化/派生版本保留差异，结构扫描、内容审阅、环境验证、任务评测分别显示。原因：当前样例存在路径差异、用途混合及特定环境脚本。一次“上传成功”不能承诺智能体可执行。

### ADR-04：模型配置版本化，实际值在运行前解析冻结

显示别名、专业职能、模型配置 ID 分离。继承显式、来源可见、参数兼容性验证、fallback 有界。代价是配置 UI 多一层，但能回答“为什么这次用了这个模型”，且模型默认更新不改历史。

### ADR-05：检验标准独立于生成者

参考数据、残差、关键门禁均为冻结只读输入，变更单独评测。原因：转换器最危险的失败是输出看似正常或为过关而放宽标准。最终仍以程序证据为核心，审查模型负责发现覆盖漏洞和解释，不能覆盖失败的确定性门禁。

### ADR-06：只保留一套费用与运行账本

专业角色、版本和评测只是现有调用账本标签。原因：多个聚合维度不应导致二次预留/结算、漏计评测或伪造实时硬上限。

### ADR-07：逐项目启用与回滚

版本发布与项目使用分开；新版本先试点，绑定切换 CAS，活动运行保留原快照。原因：客户参考软件版本、格式数据与允许例外可能不同，不能全局自动跟随。

### ADR-08：成果形式进入任务契约

图片、代码、报告、转换结果和安装包都有明确身份、验证来源、平台条件与获取入口。原因：鹈鹕案例说明提交 SHA 和 PR 状态不足以满足用户需求。交付完成看用户是否拿到所需成果，外部发布是单独状态。

## 实现前仍需实际确认的事项

这些事项不阻碍设计和本地实现，但影响真实试点：

- 服务端实际支持的模型 ID、reasoning 参数和订阅/API 凭据；不能直接使用桌面模型显示名。
- 第一批真实维护项目、参考软件版本、可用样本及共享范围。
- 工业格式工具链运行在 Linux、Windows 还是混合环境，以及所需商业参考软件/设备。
- 安装包目标 OS/架构、签名要求、单文件尺寸及保留期限。
- 是否继续可信团队共享读模式；若需要严格客户隔离，必须作为独立权限迁移完成后再导入客户私有数据。
- 当前生产服务器连接方式及部署版本；本次设计不代表已经部署。

## 设计审查自检

已覆盖：对象与复用边界、首个 Skill 的具体适配、用户路径、角色/模型矩阵、版本/覆盖/冻结、工具与环境、权限/撤销、预算/结算、数据集/残差/评测、候选沉淀、交付体验、接口/存储/事务、迁移/回滚、阶段实现与故障测试。

明确保留的范围：首版固定模板而非任意流程语言；现有宿主执行而非已完成远程 Windows 节点；实际模型待探针而非硬编码名称；真实项目试点与生产部署单独核对。


## 2026-09-09 第二版修订：按用户的新产品定位收敛

用户明确要求职能体作为项目第一入口，维护通过 chatbot 接收 Skill 和口语补充，核心保持 loop。第一版把平台配置和治理流程前置，超出了这一日常使用需求。

当前规范调整为：两种对话模式共用执行引擎；默认单职能体循环；模型按需阶段覆盖；草稿自动保存、明确应用、版本回滚；项目与成果从对话直接关联。独立评测中心、通用编排、多 Agent 团队和完整模型注册平台移出首版，关键回归、权限、版本证据仍保留。

这是基于用户反馈和既有代码边界的设计取舍；本轮没有新增外部调研，也不据此推断 Codex/ChatGPT 内部实现。历史设计在 archive 供追溯，当前 SYSTEM-DESIGN 与 LUNA-IMPLEMENTATION 为权威规范。
