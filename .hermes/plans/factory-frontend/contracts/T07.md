### 关键约束：dist 不许留在工作树

**这是踩过的坑**：`frontend/dist/*.js` 会被 `shadow_code` 影子代码闸门判为
「被 .gitignore 挡住的代码文件」，导致 `tests/test_shadow_code.py::test_this_repo_itself_reports_nothing` 失败。

`factory/harness/workspace.py:171` 的注释明确写了 `dist/` / `build/` **刻意不加进
`_VENDOR_DIRS` 豁免表**，因为那是最好藏代码的地方 —— 这个判断是对的，**不要去改那张表**。

因此：
- 生产构建产物放到**仓库外**：`/home/ubuntu/factory-web/dist`
- `frontend/package.json` 的 build 脚本加 `--outDir`，或部署脚本 build 完 `mv` 出去
- 部署脚本结尾必须 `rm -rf frontend/dist`
- `deploy/README.md` 里把这条写成显式警告

### 部署顺序（不许颠倒）
1. 先备份现有 Caddyfile 到 `~/factory-data/Caddyfile.bak.<日期>`
2. `caddy validate --config <新配置>` 通过
3. 停旧 dashboard 服务（释放 8788）
4. 起新 api 服务，`curl` 确认 8788 活着
5. build 前端到仓库外目录
6. `caddy reload`
7. 浏览器验证
8. `rm -rf frontend/dist`（若 build 落在了仓库内）
9. 跑一遍 `pytest tests/test_shadow_code.py`

### 回退命令（写进 README）
```bash
sudo systemctl stop factory-api && sudo systemctl disable factory-api
sudo cp ~/factory-data/Caddyfile.bak.<日期> /etc/caddy/Caddyfile
sudo caddy validate --config /etc/caddy/Caddyfile && sudo systemctl reload caddy
```

### 不包含（边界说明）

- 不做 CI/CD 自动部署

### 技术约束
- CLI 是 argparse：`sub.add_parser("api", ...)` + `set_defaults(func=_cmd_api)`
- API 绑 `127.0.0.1`，外部访问一律走 Caddy（同 dashboard 的取舍）
- systemd 单元照 `deploy/factory-worker.service` 的写法
- Caddy 改动前必须 `validate`，失败不许 reload
